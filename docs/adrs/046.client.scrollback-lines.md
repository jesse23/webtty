# ADR 046: client — Scrollback in lines

**SPEC:** [config](../specs/config.md), [client](../specs/client.md)
**Status:** Accepted
**Date:** 2026-10-13

---

## Context

The client passes `Math.ceil(config.scrollback / 80)` to the terminal as its scrollback limit (ADR 041). `scrollback` is the server's replay buffer in characters (default 262,144), so the terminal gets 3,277, which both engines read as bytes:

- The Coder wasm keeps about 500–650 rows at 120 columns.
- The official engine (ADR 042) passes it to `SCROLLBACK_MAX_BYTES`. Ghostty prunes whole pages, so it keeps what fits in the pages it allocates, again far below what the setting suggests.

A user who wants more history has to raise `scrollback` about 80 times, which also grows the server's replay buffer.

The official C API limits scrollback in lines (`GHOSTTY_TERMINAL_OPT_SCROLLBACK_MAX_LINES`) and in bytes (`…_MAX_BYTES`), both `size_t*`, and whichever limit is reached first applies. A NULL pointer removes that limit; 0 bytes disables scrollback and erases it. Both are page-granular: the header says the line limit keeps somewhat more than asked, but on the pinned wasm it prunes to a little under (below), and the byte limit is within about a page (about 400 KB). The wasm's default byte limit is 10,000 bytes, so a line limit alone keeps almost nothing.

## Decision

A new client config key, `scrollbackLines`, sets the terminal's history in lines. ADR 041 step 4.

- **`scrollbackLines`:** number, default `10000`. `0` means no line limit. Other values are floored to whole lines; negative or non-finite values are ignored (default). Re-read on tab reload, like the other terminal appearance keys, and served by `/api/config`.
- **Official engine:** `SCROLLBACK_MAX_LINES` is `scrollbackLines` (a NULL pointer for `0`), and `SCROLLBACK_MAX_BYTES` is always 32 MiB, so memory stays bounded with no line limit.
- **Coder engine:** unchanged. It keeps the derived byte limit until it is deleted (ADR 041 step 5).
- **`scrollback`** keeps its meaning, the server's replay buffer in characters; only the Coder engine still derives its limit from it.

## Consequences

- With the official engine, the terminal holds about `scrollbackLines` lines of history, unless 32 MiB fills first: wide terminals with many styles or graphemes hold fewer. Page granularity lands a little under the limit. Measured on the pinned wasm with plain lines:

  | Setting | Columns | Lines kept |
  |---|---|---|
  | derived limit today (3,277 bytes) | 120 | 584 |
  | `scrollbackLines: 10000` | 120 | 9,682 |
  | `scrollbackLines: 10000` | 300 | 9,886 |
  | `scrollbackLines: 500` | 80 | 266 |
  | `scrollbackLines: 0` (40,000 written) | 80 | 39,977 |
- Memory per tab grows with history instead of staying near one page. ADR 041's Node figures were about 11 MB at 10,000 lines of plain text at 120 columns and 25 MB of heavy truecolor; this ADR's measurements in headless Chrome are below.
- **Config migration:** none required. A user who raised `scrollback` to get more history keeps a larger replay buffer and gets 10,000 lines of history on the official engine; to change that, they set `scrollbackLines`.
- On the Coder engine (still the default) nothing changes, and `scrollbackLines` has no effect.

## Considered Options

- **Keep deriving the limit from `scrollback`.** One key, but it couples the server's replay buffer to the terminal's history and stays in bytes, which nobody can reason about.
- **A byte limit key.** Matches the C API, but page granularity and styles make bytes a poor proxy for "how far back can I scroll".
- **No byte ceiling with `scrollbackLines: 0`.** Truly unlimited, but one long `cat` could take a tab's memory without bound.
