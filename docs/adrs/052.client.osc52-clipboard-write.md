# ADR 052: client — Programs write the clipboard with OSC 52

**SPEC:** [client](../specs/client.md), [config](../specs/config.md)
**Status:** Accepted
**Date:** 2026-10-14

---

## Context

Programs that cannot reach the clipboard of the machine the user sits at copy with OSC 52: `ESC ] 52 ; c ; <base64> BEL` (or ST). Claude Code and pi do it over SSH, Neovim 0.10+ has a built-in OSC 52 provider, and tmux does it with `set-clipboard`. webtty ignored the sequence, so a copy in any of them over SSH inside webtty went nowhere. (Locally they use pbcopy or similar, which works without the terminal.)

Ghostty's official libghostty-vt, the engine since ADR 042 and ADR 047, parses OSC 52, iTerm2's `OSC 1337 ; Copy=:<base64>` and kitty's OSC 5522 clipboard protocol, decodes the base64 and calls one callback, `GHOSTTY_TERMINAL_OPT_CLIPBOARD_WRITE`, with a `GhosttyClipboardWrite`: a location (standard, selection, primary), a list of MIME representations (one `text/plain` for OSC 52), and a `reply` the callback must call before it returns. A NULL callback, the default, ignores OSC 52 and OSC 1337 writes and refuses OSC 5522 writes with ENOSYS. Reads (`OSC 52 ; c ; ?` and OSC 5522 reads) go to a separate callback, `CLIPBOARD_READ`; NULL, its default, ignores them. At the pinned commit (`05dcf887`):

- **Selection characters** (`stream_terminal.zig`, `clipboardContents`): `s` is the selection clipboard, `p` the primary, and anything else (`c`, an empty field, `0`, ...) the standard clipboard. More than one character (`pc`) is not a valid sequence and is dropped. Ghostty on macOS writes `s` to a private pasteboard of its own (`com.mitchellh.ghostty.selection`), not the system one, and drops `p` ("macOS has no primary selection").
- **Decoding**: strict base64; a character outside the alphabet drops the whole write (never partially decoded), and missing padding is accepted. An empty payload is a clear (no representations). The bytes are passed as they are, with no UTF-8 check.
- **Size**: an OSC is limited to 8 MiB (`MAX_ALLOCATING_BUF`), sequence body included, so an OSC 52 carries a little under 6 MiB of text. A longer one is dropped whole and the terminal carries on. OSC 5522 writes have their own limit, 64 MiB by default (`CLIPBOARD_WRITE_MAX_BYTES`).
- **Policy**: Ghostty's `clipboard-write` defaults to `allow` (`ask` and `deny` exist), and `clipboard-read` to `ask`.

The browser side has its own rules. `navigator.clipboard.writeText` exists only in a secure context (https or localhost). Chrome writes only while the document has focus; Firefox only shortly after user input (transient activation); Safari only inside the user input's own event handler, so a write that arrives over the WebSocket after a key press is refused there. None of them lets a page write the clipboard long after the user last touched it.

And webtty has something a native terminal does not: on every connect, the server replays the session's recent output (ADR 007, ADR 048). An OSC 52 in that history would write the clipboard again on every reload or reconnect, replacing whatever the user copied since with something copied long ago.

The user asked for OSC 52, writes only, with a switch.

## Decision

### Writes only

Only writes are honoured. `CLIPBOARD_READ` is never set, so an `OSC 52 ; c ; ?` query gets no answer, as with libghostty-vt's default (Ghostty itself asks; webtty has no prompt, and a page reading the clipboard needs its own permission). Nothing is ever sent back for OSC 52.

### The binding takes the write and answers it

`ghostty.ts` installs a `CLIPBOARD_WRITE` callback when the terminal is created with `clipboardWrite` on (the new `GhosttyTerminalConfig.clipboardWrite`, default true), and leaves it NULL otherwise. The callback:

- writes nothing for the selection or primary location, and answers `UNSUPPORTED`: the browser has one clipboard, and Ghostty on macOS keeps both away from the system clipboard too;
- for the standard location, takes the first plain-text representation (Ghostty's `isTextMime` names: `text/plain`, `text/plain;charset=utf-8`, `UTF8_STRING`, `TEXT`, `STRING`), decodes it as UTF-8 with invalid bytes replaced by U+FFFD (`writeText` takes a string; Ghostty on macOS stores the bytes as they are), and answers `SUCCESS`; with no text representation, `UNSUPPORTED`;
- for a clear (no representations), keeps `''`: an empty clipboard, as Ghostty on macOS gets when it writes an empty string.

The text is kept until `readEffects`, which gains `clipboard` (the last write since the previous call, `''` for a clear, or null), like the bell and title. The reply only matters for OSC 5522, which has an acknowledgement; it is sent before the browser write, which happens later and asynchronously.

OSC 1337 Copy and OSC 5522 writes come through the same callback and are handled the same way. Ghostty's size limits and base64 handling are kept as they are; webtty adds none.

### The terminal reports it; `index.ts` writes it

`Terminal` fires the new `onClipboardWrite(text)` after a write whose effects carry a clipboard write, and passes its new `clipboardWrite` option to the engine. `index.ts` hands the text to `ClipboardWriter` (`src/client/clipboard-write.ts`), which calls `navigator.clipboard.writeText`:

- **Held back after each connect until the user acts in the tab.** `connected()` disarms it at every (re)connect, and `userInput()`, on any `keydown`, `mousedown`, `paste` or `drop` in the window, arms it. So the replay never writes the clipboard, and a write from the live session always follows the user doing something in the tab, which is also when browsers allow it.
- **Failures are logged once, with no error UI.** No clipboard API (an http page that is not localhost), a refused write (no focus, no activation, Safari), and a write held back for the replay are each logged to the console once per page. The program is never told: OSC 52 has no reply.

### Config

`clipboardWrite` (boolean, default `true`), served by `/api/config` and read on every tab reload. `false` leaves the callback unset, so OSC 52, OSC 1337 Copy and OSC 5522 writes are ignored by Ghostty. It is a boolean rather than Ghostty's `allow`/`ask`/`deny`: webtty has no prompt to ask with.

## Consequences

- `"+y` in Neovim, a copy in Claude Code or pi over SSH, and tmux with `set-clipboard on` reach the browser clipboard in Chrome and Firefox (in Firefox, if the copy follows the key or click within its activation window). UTF-8 text arrives intact, newlines included.
- In Safari, most OSC 52 writes are refused by the browser; the console says so once.
- A reload, a reconnect, or the replay after a tab fell behind (ADR 048) does not write the clipboard. A write that arrives after reconnecting but before the user presses a key or clicks in the tab is ignored, and so is a replay still arriving after the user started typing.
- `"*y` in Neovim (`p`) and writes to the selection clipboard (`s`) do nothing, as in Ghostty on macOS.
- A program can replace the clipboard without asking, as in Ghostty's default (`clipboard-write = allow`); `clipboardWrite: false` turns that off.
- Programs cannot read the clipboard.

## Considered Options

- **Write only, held back until input (chosen).**
- **Answer reads too.** Needs a prompt webtty does not have, a separate browser permission, and lets any program in the session read what the user copied elsewhere.
- **Write the system clipboard for `s` and `p` too** (as some terminals do). Ghostty keeps them apart on macOS; Neovim sends `*` as `p`, and following Ghostty keeps `"+y` and `"*y` meaning what they mean there.
- **Write every OSC 52, the replay included.** Every reload would overwrite the clipboard with an old copy.
- **Ignore OSC 52 in the replay by marking where it ends.** Needs a protocol change (the replay is not delimited), and a write while the user is away from the tab would still be refused by the browser.
- **`allow` / `ask` / `deny` like Ghostty.** `ask` needs a prompt; a boolean covers the rest.
- **Fall back to `document.execCommand('copy')`.** Needs user activation in the same way, so it fails where `writeText` fails.
