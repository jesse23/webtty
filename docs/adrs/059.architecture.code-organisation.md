# ADR 059: architecture — Code organisation and conventions

**SPEC:** [architecture](../specs/architecture.md)
**Status:** Accepted
**Date:** 2026-10-14

---

## Context

webtty grew feature by feature, each ADR adding to whichever file was nearest. The result works, and much of it is well factored (`OutputPacer`, `ReplayWindow`, `OutputAck`, `search.ts`, `glide.ts` are small, pure and fully tested), but the structure no longer helps a reader:

- **Large files.** Five vendored files hold about 8,300 lines (`ghostty.ts` 3061, `terminal.ts` 2147, `renderer.ts` 1508, `input-handler.ts` 856, `selection-manager.ts` 736); `graphics.ts` is 662, `index.ts` 565, `routes.ts` 485. Each mixes several unrelated jobs.
- **Untestable entries.** `src/client/index.ts`, `src/server/index.ts` and `src/cli/index.ts` run their logic at import time, so the client wiring has no tests at all, and the server routes and WebSocket layer are tested only through subprocesses and do not appear in coverage.
- **Duplicated contracts.** The client re-declares `Theme`, `KeyboardBinding` and `ClientConfig`; the server whitelists the same keys a third time. The WebSocket close codes are numbers in the client and constants in the server. Runtime detection (`isBun`) has three definitions with three meanings.
- **No stated rules.** Nothing says where a new module goes, what it may import, how big it may grow or how it is tested. `client.md`'s source layout is out of date (it lists `index.html`, and calls the vendored code unchanged).

The user asked for a code base that is easy to read and maintain and ready to grow: short files with one purpose and a good name, the right pattern for each, clear comments, a folder structure that makes sense, and test coverage as high as possible, with testability a design driver. No framework and no new runtime dependency.

## Decision

Adopt the organisation in the [architecture SPEC](../specs/architecture.md) and refactor the code base to it in small, behaviour-preserving steps.

### Layers and imports

- Client, server and CLI are separate layers. The client imports nothing from the server, CLI or PTY, and nothing from Node; it imports **types only** from `src/config` (`import type`, erased from the bundle). The server and CLI never import the client; the CLI never imports the server.
- In the client: entry → composition root → features → connection, layout and app modules → the vendored layer through its barrel only → vendored internals. Features never import each other.
- The vendored ghostty-web layer imports nothing outside itself.

### Contracts across the client/server line

There is no `src/shared` folder. Config types are defined once in `src/config` and the client derives `ClientConfig` from them with `Pick<Config, …>`; the server's `/api/config` key list becomes one constant (`CLIENT_CONFIG_KEYS`) next to that type, pinned by a test. The three close codes the client acts on are mirrored in `src/client/connection/close-codes.ts` and pinned to the server's by a contract test. A shared value module would have to be kept free of Node by convention; a type import is erased, and a two-line constant mirror with a test is cheaper than a third top-level layer.

### Module kinds, naming and comments

- Each file is one kind (entry, composition root, feature, service, object, view, util, adapter, constants, types, facade), named in its header comment.
- Files are kebab-case and named after their main export. Folders name a domain (`connection/`, `sessions/`, `render/`), never a kind (`utils/`, `services/`). `utils.ts`, `helpers.ts`, `misc.ts`, `common/` and folder-root `types.ts` are banned.
- Each file starts with a one-to-three-sentence header (what, kind, ADRs). Each export has a JSDoc line. Comments say why; no section banners.

### Size limits

App, server, CLI, config, pty and script files aim at 200 lines and stop at 300. Vendored files aim at 400 and stop at 600; the facades have lower limits (SPEC). Two data tables and the per-cell decode hot path are exempt, each with its reason written next to it. Test files stop at 800.

### Enforcement

`scripts/check-architecture.ts` walks `src/` and `scripts/` and checks the size limits and the import rules; `scripts/check-architecture.test.ts` runs it under `bun test`, so CI's test job enforces it. While the refactor runs, files over their limit today are listed in a **ratchet allowlist** with their current line count: they may shrink or disappear, never grow, and each step removes the entries it fixes. No dependency is added: the checker reads files and import specifiers with plain string matching.

### How the refactor is done

- Moves use `git mv` and carry no logic change; a module's tests move in the same commit.
- Each commit passes `bun test`, `bun run lint` and `bun run build`.
- Behaviour, wire protocol, config keys, CLI output, HTTP routes and bodies, `dist/` names and the entries named by `scripts/build.ts` and `package.json` stay the same. The one deliberate behaviour change, releasing listeners that `dispose()` leaks today, is its own commit and its own record ([ADR 065](065.client.listener-teardown.md)).
- The server/CLI track and the client track touch disjoint files, so they can proceed in parallel.

## Considered Options

- **Keep the structure, document it.** Cheapest, but leaves the untestable entries and the 2,000-to-3,000-line files, which is what makes the code hard to change.
- **A framework or DI container** (for the client, React or a signals library; for the server, Express or Hono). Rejected: the client is one view and the server a dozen routes; a framework adds a runtime dependency and a second mental model, and none of the problems above is one a framework solves.
- **Split by kind** (`models/`, `services/`, `utils/`). Rejected: a feature's code ends up in four folders, and a folder name says nothing about what is inside.
- **A `src/shared` folder for contracts.** Rejected for now (above); revisit if the client needs more server values than three close codes.
- **A lint plugin for import rules** (`eslint-plugin-boundaries`, `dependency-cruiser`). Rejected: a new devDependency and a second linter for six rules a 150-line script checks.

## Consequences

- A reader can find any behaviour from the SPEC's tree, and each file states what it is and why.
- The client wiring, the server routes and the WebSocket layer become importable and testable in-process, so coverage measures them.
- The checker keeps the structure from eroding: an oversized file or a wrong import fails `bun test`.
- The refactor is large (about 12,000 lines move). Doing it in steps that each keep the suite green, with moves separate from logic changes, keeps any regression small and bisectable. `git blame` on moved lines goes through `git log --follow`.
