# ADR 032: Client — Kitty graphics via client-side APC interception and overlay canvas

**SPEC:** [kitty-graphics](../specs/kitty-graphics.md)
**Status:** Accepted
**Date:** 2026-09-20

---

## Context

TUI programs that draw pixels (`kitten icat`, `yazi` previews, and
[terminal-browser](https://github.com/zenbu-labs/terminal-browser), which
streams a real Chromium into the terminal) use the
[kitty graphics protocol](https://sw.kovidgoyal.net/kitty/graphics-protocol/):
APC sequences of the form `ESC _ G <keys> ; <base64 payload> ESC \`.

webtty's terminal core is ghostty-web (WASM build of Ghostty's VT parser). Its
WASM parses APC (`apc_start/apc_put/apc_end`) but discards the payload: there
is no image storage, no placement API, and the canvas renderer has no image
layer. The result is that graphics sequences are silently dropped and the
program shows nothing (and, for programs that probe first with `a=q`, decides
the terminal does not support graphics).

Every byte a PTY emits already passes through one place in the client,
`ws.onmessage` → `term.write()`, and `Terminal.write()` is synchronous into the
WASM, so the cursor position is exact between two `write()` calls.

## Decision

Implement the protocol in the webtty client, in front of ghostty-web:

1. **Stateful APC splitter** (`src/client/kitty.ts`). Split each PTY chunk into
   plain text and APC commands. State survives across chunks because a
   sequence can be split over WebSocket frames and images arrive as `m=1`
   chunks. Every APC is removed from the text handed to `term.write()`.
2. **Interleaved processing.** For each command: `term.write()` the text
   before it, then read cursor/scroll state and handle the command, then
   continue. This keeps placement positions exact.
3. **Overlay canvas** (`src/client/graphics.ts`) positioned over the terminal
   canvas, `pointer-events: none`, drawn from a placement table keyed by
   image id + placement id. Placements are anchored to an absolute row
   (scrollback length + cursor row) so they scroll with text.
4. **Transmission support (POC):** `t=d` only (direct, chunked), `f=24 / 32 /
   100` (RGB, RGBA, PNG), `o=z` (zlib, via `DecompressionStream`). `a=T`
   (transmit + display), `a=t`, `a=p`, `a=d` (`a`, `A`, `i`, `I`), `a=q`.
   `t=f` / `t=t` / `t=s` are answered with an error, which is correct for a
   browser and makes well-behaved clients fall back to `t=d`.
5. **Cursor movement** after a placement follows the spec (`C=0` moves the
   cursor past the image, `C=1` does not) by injecting the equivalent
   `LF` / `CHA` into the `term.write()` stream.
6. **Query replies.** `a=q` and transmit/display responses
   (`ESC _ G i=<id>;OK ESC \`) are sent back over the WebSocket as if typed.
   Programs that size their output in pixels ask with `CSI 14 t` / `16 t` /
   `18 t`; the client answers these itself from the renderer metrics, because
   the WASM cannot know pixel size.
7. **Pixel scale is `devicePixelRatio`.** Sizes reported to programs are
   device pixels, as kitty and Ghostty report them, and images are drawn at
   `size / scale` CSS pixels. Programs rely on this: terminal-browser divides
   the reported size by the display scale factor to get CSS pixels (skipping
   that only for terminals flagged as reporting CSS pixels, currently VS
   Code), so reporting CSS pixels made its pages lay out at 2x and its UI
   draw at half size. The cost is that a full-window frame on a 2x display is
   4x the pixels to send and decode; measure before optimising. Cell sizes are
   whole device pixels (`round(cssCell * devicePixelRatio)`) and the
   CSS-to-device scale is derived per axis from that snapped cell, not from
   `devicePixelRatio` directly. Programs size frames as `cols x cell`, so with a
   fractional ratio (1.25 / 1.5 / 1.75, common on Windows) dividing by the raw
   ratio drifts up to half a pixel per column and the image no longer lines up
   with the grid or the mouse mapping. Each placement records the scale it was
   sized for, so a later zoom or monitor change does not rescale images already
   on screen.
8. Placements are cleared on screen clear (`CSI 2 J`, `CSI 3 J`), alt-screen
   switch (`?1049` / `?47`), and full reset (`ESC c`).

## Considered Options

**Option A: Upstream — build kitty graphics into ghostty-web (deferred)**
Ghostty proper implements the protocol in Zig, so the emulator would then know
placements, overwrite semantics, and scrollback for free, and every
ghostty-web consumer would benefit. It needs a rebuilt WASM with the feature
enabled, a new placement API, and an image layer in the canvas renderer, all
in a separate repo with its own release process. Deferred: this ADR is scoped
to something webtty can ship alone, and the client-side POC will show which
API is actually needed.

**Option B: Server-side transcoding (rejected)**
Convert graphics to something ghostty-web can draw (half-block characters,
sixel-like). Loses the point of the protocol (real pixels) and still needs a
client image layer.

**Option C: Client-side interception + overlay canvas (chosen)**
Small, self-contained, needs no change to the server, WASM, or PTY.

## Consequences

- `kitten icat`-style display and streaming full-window apps such as
  terminal-browser (standalone mode) work in the browser.
- The emulator is unaware of images, so text written over an image does not
  erase it. Screen clears and alt-screen switches clear placements, which
  covers full-screen TUIs; ordinary shell output overwriting an image is a
  known gap.
- Out of scope for the POC: unicode placeholders (`U=1`, used by
  tmux and terminal-browser's embedded mode), `t=f` / `t=s`, animation frames,
  z-index layering under text, and pixel-precise mouse (`?1016`).
- **Scrollback replay.** The server keeps a character-capped scrollback and
  replays it to new connections. Image payloads will fill and truncate it,
  and a replay can begin in the middle of an APC. The splitter must tolerate
  a stray tail, and the server should stop storing APC payloads in
  `session.scrollback`; tracked as a follow-up, not part of this ADR.
- Every APC is swallowed by the client, including non-graphics ones, matching
  what ghostty-web does today.
- If upstream ghostty-web gains graphics support, the splitter, overlay and
  reply logic become redundant and this ADR should be superseded.
