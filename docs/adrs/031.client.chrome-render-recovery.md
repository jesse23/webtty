# ADR 031: Client — Recover from Chrome-only stale hit-test grid and stale canvas

**SPEC:** [client](../specs/client.md)
**Status:** Accepted
**Date:** 2026-09-10

---

## Context

Two related symptoms were reported, both reproducing only in Chromium-based
browsers (Chrome, Vivaldi) and never in Firefox:

1. **Clicks land on the wrong target after a reload.** A UI element visibly
   present in the terminal (rendered by a TUI app over the PTY) sometimes does
   not respond to a click, intermittently, only after a hard reload.
2. **A tab switch sometimes leaves a blank/partial repaint.** Switching away
   from and back to a webtty tab in Chrome can leave stale or partially
   redrawn canvas content until something happens to change; Firefox always
   redraws correctly.

Both trace to the same underlying pattern: ghostty-web's `CanvasRenderer`
caches state (font metrics, canvas pixel contents) and only refreshes it
reactively, on the assumption that whatever invalidated the state will also
trigger a normal repaint. Chromium has two behaviors that violate that
assumption; Firefox does not exhibit either.

### Why only Chrome — stale hit-test grid

`CanvasRenderer.measureFont()` (`ghostty-web/lib/renderer.ts`) runs
synchronously inside the constructor, invoked from `Terminal.open()`
(`webtty` calls this via `await term.open(container)`). It measures
`config.fontFamily` with `ctx.measureText('M')` immediately, with no wait on
`document.fonts.ready`.

If the custom terminal web font has not finished loading yet, the canvas 2D
context silently substitutes a fallback font for the measurement — no error,
no async signal. The resulting `charWidth`/`charHeight` feed directly into
`getCellDimensions()`, which the mouse handler uses to convert a click's pixel
position into a terminal cell. Once the real font loads a moment later, glyphs
repaint correctly, but the hit-test grid stays sized to the fallback font's
metrics — clicks a fraction of a cell off from where they appear can resolve
to the wrong cell.

This is a race, not a guaranteed failure, which is why it is intermittent
("sometimes"). Chromium's web font pipeline (fetch → parse → swap) is
asynchronous relative to first paint by design (FOUT), and its timing varies
run to run — especially on a cold reload where the font is re-fetched from
disk cache rather than already resident. Firefox's historical behavior here
differs enough in practice that the terminal's font is consistently ready (or
close enough) by the time `measureFont()` runs, so the race rarely — if
ever — loses.

Notably, `CanvasRenderer` already exposes `remeasureFont()` with a doc-comment
saying "call after font loads or changes" — but nothing in ghostty-web or
webtty ever called it. The intended fix already existed; it was just never
wired up.

### Why only Chrome — stale canvas on tab switch

`Terminal`'s render loop (`startRenderLoop` in `ghostty-web/lib/terminal.ts`)
runs continuously via `requestAnimationFrame` and always renders with
`forceAll = false` — i.e. it trusts the WASM terminal's own dirty-row
tracking and repaints only rows that changed.

Chromium is known to reclaim GPU memory from backgrounded tabs by evicting or
clearing canvas/WebGL backing stores; Firefox is markedly less aggressive
about this. When the tab regains visibility, the canvas can come back
blank or partially cleared, but nothing in the PTY stream changed — so no
rows are marked dirty, and the non-forced render loop has no reason to redraw
them. The stale/blank canvas persists until unrelated PTY output happens to
touch those rows.

---

## Decision

Address both gaps in `src/client/index.ts` by triggering the same
forced-full-repaint primitive already established in
[ADR 015](015.client.cursor-ghost-repaint.md) at the two moments Chrome's
behavior can silently desync client-side render state:

1. **Font-ready remeasure.** On `document.fonts.ready`, call
   `term.renderer.remeasureFont()`. This alone is sufficient: the running
   render loop compares `canvas.width` against
   `dims.cols * metrics.width * devicePixelRatio` on every frame and already
   calls its own internal forced-resize-and-repaint when they disagree, so
   the very next animation frame after remeasuring self-corrects both the
   glyph grid and the hit-test grid together. No manual `fit()` or `render()`
   call is needed.

2. **Visibility-restore repaint.** On `visibilitychange`, when
   `document.visibilityState === 'visible'`, call
   `term.renderer.render(term.wasmTerm, true, term.viewportY)` — the same
   `forceAll = true` call ADR 015 uses for the DECSCUSR ghost-cursor fix. This
   bypasses dirty-row tracking and unconditionally repaints every row,
   overwriting whatever Chrome's GPU memory reclamation left behind.

Both hooks are cheap and infrequent (once per font load, once per tab
visibility change), so there is no per-frame or per-keystroke cost.

---

## Considered Options

**Option A: Fix at the source in ghostty-web (rejected for this change)**

The correct long-term fix is in ghostty-web itself: await
`document.fonts.ready` before the first `measureFont()` call, and add a
`visibilitychange` listener inside `Terminal` that forces a repaint. This
would fix the bug for every ghostty-web consumer, not just webtty. Deferred
because ghostty-web is a separate package/repo with its own release process;
the workaround here is scoped to unblock webtty immediately using only
already-public `Terminal` surface (`term.renderer`, `term.wasmTerm`,
`term.viewportY` — the same properties ADR 015 established as public "for
FitAddon"/consumer use).

**Option B: Poll for font readiness / canvas staleness (rejected)**

Periodically re-measure fonts or force-repaint on a timer. Wastes cycles for
an event that has a precise, cheap-to-observe signal
(`document.fonts.ready`, `visibilitychange`) in both cases.

**Option C: Event-driven remeasure + forced repaint (chosen)**

Hooks directly into the two browser events that correspond to the actual
state transitions, with no polling and no guessing at timing.

---

## Consequences

- Mouse clicks in Chrome/Vivaldi correctly target the cell under the pointer
  even when the terminal font was still loading at `Terminal.open()` time.
- Switching back to a backgrounded Chrome tab always repaints the full
  terminal, matching Firefox's existing behavior.
- If ghostty-web adopts Option A upstream (awaits font readiness internally
  and/or adds its own `visibilitychange` handling), both hooks in
  `index.ts` become redundant no-ops and can be removed, and this ADR should
  be superseded.
- `document.fonts.ready` and `visibilitychange` are both listened to for the
  lifetime of the page; neither is ever removed, matching the existing
  lifetime of the WebSocket connection and terminal instance.
