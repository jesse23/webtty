# ADR 037: client — Preserve text when bracketed paste is off

**SPEC:** [client](../specs/client.md)
**Status:** Accepted
**Date:** 2026-09-21

---

## Context

The client currently forwards Ctrl+V (`\x16`) for multiline clipboard text when terminal mode 2004 is off. A remote TUI can interpret that key as an image-paste shortcut and insert an image path instead of the text. The fallback also depends on the remote process being able to read the host clipboard, which is not generally possible across remote sessions. Single-line text is already sent directly; non-text clipboard content intentionally uses Ctrl+V (ADR 014).

Without bracketed-paste mode, the terminal has no generic way to tell the receiving process that embedded newlines are pasted text rather than Enter presses. Sending bracket delimiters to an app that does not support them would insert control sequences; sending Ctrl+V is not a text paste.

## Decision

Send nonempty text to the PTY regardless of mode 2004: wrap multiline text in bracketed-paste delimiters only when mode 2004 is enabled. Otherwise send the original text without delimiters, as a conventional terminal paste. Keep Ctrl+V exclusively for empty/non-text clipboard contents (or a failed clipboard read on the Ctrl+V key path). Use the same policy for the browser paste event and Ctrl+V clipboard read.

## Consequences

- Multiline text no longer becomes an image-paste shortcut when mode 2004 is off; apps that do not accept bracketed paste never receive bracket delimiters.
- A receiving app without bracketed paste may treat newlines as Enter, potentially submitting commands or accepting an fzf selection. There is no universal, application-independent way to ensure atomic multiline editing in such an app. Users should not paste untrusted multiline commands into an unbracketed shell or prompt. A nested app must enable/propagate mode 2004 for safe multiline editing.
- Image-only clipboard paste still forwards Ctrl+V, preserving the existing native clipboard path from ADR 014.
