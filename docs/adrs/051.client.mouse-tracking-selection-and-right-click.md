# ADR 051: client — Drag, double click and right-click follow app mouse tracking

**SPEC:** [client](../specs/client.md), [config](../specs/config.md)
**Status:** Accepted
**Date:** 2026-10-14

---

## Context

webtty listens to the mouse in two places, and neither asks the other:

- `input-handler.ts` reports every press, release and drag to the app while it tracks the mouse (any of DEC modes 9, 1000, 1002, 1003), encoded by Ghostty (ADR 049).
- `selection-manager.ts` starts a selection on every left press, and selects a word or line on a double or triple click, whether or not the app tracks the mouse. With `copyOnSelect` on (the default, ADR 011), the release copies it.

So in an app that tracks the mouse (vim with `set mouse=a`, htop, tmux, Claude Code and pi in fullscreen), a drag both reached the app and drew webtty's highlight, and the release wrote the clipboard. Claude Code and pi copy on release themselves, through the native clipboard on the machine they run on (pbcopy, PowerShell `Set-Clipboard`, wl-copy or xclip; OSC 52 only over SSH), so webtty's copy overwrote theirs with whatever cells happened to be under its own highlight. A double click in vim selected a word in vim and another in webtty.

The right button had the same split. The app got the press and release, and the browser showed its context menu over the app. `rightClickBehavior` (ADR 011) had two values: `"default"` (browser menu) and `"copyPaste"` (copy and clear an existing selection, otherwise the menu), applied in `index.ts`, while `selection-manager.ts` moved its textarea under the pointer for every `contextmenu` so the menu offers Copy and Paste.

Native terminals agree on what to do:

- Ghostty, kitty, WezTerm, xterm, Windows Terminal and VS Code send clicks, drags and right-clicks only to an app that tracks the mouse, and select nothing themselves. Shift is the bypass: Shift+drag selects in the terminal and sends nothing to the app. Claude Code's docs tell users to hold Shift for a native selection in terminals like webtty (Terminal.app uses Fn, iTerm2 Option).
- The right button is configurable: Ghostty's `right-click-action` (`context-menu`, `paste`, `copy`, `copy-or-paste`, `ignore`), VS Code's `terminal.integrated.rightClickBehavior` (`default`, `copyPaste`, `paste`, `selectWord`, `nothing`). Windows Terminal copies a selection or pastes on right-click.

The user agreed the design below.

## Decision

### One decision for the pointer

A new module, `mouse-route.ts` in the vendored terminal, holds the rule, and both listeners call it:

- `pressToApp(tracking, shiftKey)`: a press goes to the app when the app tracks the mouse and Shift is not held. Otherwise it is webtty's.
- When the press is the app's, `selection-manager.ts` starts no selection: no highlight, no copy on release, and a double or triple click selects no word or line. An existing selection is left alone. `input-handler.ts` reports the press, the drag and the release, as today, and marks them as mouse reports: `Terminal` clears the selection for keys, text and paste, not for a mouse report, so a Shift selection outlives the app's hover (any-motion mode 1003) and clicks, and Shift+right-click or the menu's Copy still finds it.
- When the press is webtty's because Shift is held, `input-handler.ts` reports nothing for that button: not the press, not the motion while it is held, not its release, even if Shift is let go mid-drag. `selection-manager.ts` selects and copies as it does without tracking (Ghostty and xterm do the same).
- Without tracking, nothing changes: drag, double and triple click select, and the release copies when `copyOnSelect` is on.

### One function for the right button

`rightClickAction` in the same module decides what a `contextmenu` event does, from whether the app tracks the mouse, Shift, whether the menu came from the keyboard, `rightClickBehavior` and whether there is a selection:

| | Result |
|---|---|
| App tracks the mouse, right button without Shift | `app`: the app already got the press and release; the browser menu is suppressed (`preventDefault`) |
| Shift+right-click, a keyboard menu (Menu key, Shift+F10), or the app does not track the mouse | `rightClickBehavior` |
| `"contextMenu"` (default) | `menu`: the browser menu, with the textarea under the pointer so it offers Copy and Paste |
| `"copyPaste"` | with a selection, `copy`: copy it and clear it; without, `menu` (ADR 011's behaviour) |
| `"paste"` | `paste`: paste the clipboard as Ctrl+V does (ADR 037, ADR 049: `ghostty_terminal_paste`, or `\x16` for an empty or non-text clipboard) |
| `"none"` | nothing, and no menu |

A menu is from the keyboard when no right press (or macOS Ctrl+click, which opens the menu with the left button) came since the last key press: the terminal notes such a press on `mousedown` and forgets it on `keydown` and once a `contextmenu` has used it. This covers the menu opening on press (macOS, Linux) and on release (Windows).

`Terminal` owns the one `contextmenu` listener (capture, on the container) and acts on the result: `menu` calls the selection manager's textarea placement, `copy` copies and clears, `paste` fires the new `onPasteRequest`, which `index.ts` answers with the same clipboard read as Ctrl+V, and `app` and `none` cancel the menu. The `index.ts` listener for `"copyPaste"` and the selection manager's own `contextmenu` listener go. A future `"webtty"` value, a menu drawn by webtty, is one more case of `rightClickAction` and one more action; it is reserved here and not added.

### Config

- `rightClickBehavior`: `"contextMenu"` (default), `"copyPaste"`, `"paste"`, `"none"`. `"default"`, the old name of `"contextMenu"`, is still accepted. Any other value falls back to `"contextMenu"`. The default is the same on every platform; Windows Terminal users may prefer `"copyPaste"`.
- `copyOnSelect` now reads as: copy a selection made with the mouse when the mouse button is released, then clear it, as Claude Code and pi clear their own selections once copied. A drag the app receives is not a selection. With `copyOnSelect` off the selection stays, to copy with Cmd+C, Ctrl+Shift+C (ADR 054) or the menu.

## Consequences

- In an app that tracks the mouse, a drag and its release reach only the app. webtty no longer draws a highlight over it or overwrites the clipboard the app just wrote, and a double click no longer selects a second word.
- Shift+drag, Shift+double and Shift+triple click select in webtty in such an app, and the app gets nothing. Apps that read Shift+click (rare; Shift is the bypass in every native terminal) lose it.
- A right-click in such an app shows no browser menu. Shift+right-click, or the keyboard, shows it (or does what `rightClickBehavior` says).
- Without tracking (a shell, `less` without `--mouse`), the left button behaves as before, and right-click as before for `"contextMenu"` (the old `"default"`) and `"copyPaste"`.
- The keyboard menu depends on the browser opening one. While the terminal has focus, the Menu key and Shift+F10 are keys like any other: they are encoded and sent to the app (`CSI 29 ~`, `CSI 21 ; 2 ~`), as native terminals do, and the browser opens no menu (checked in headless Chrome). A `contextmenu` aimed at the terminal with no right press before it, such as one opened by assistive technology, follows `rightClickBehavior`. One aimed elsewhere in the page never reaches the terminal's listener and shows the browser menu.
- The decision is two small pure functions with unit tests; the listeners only call them.

## Considered Options

- **Follow tracking, Shift to bypass (chosen).** What every native terminal does, and what Claude Code tells its users to do.
- **Keep selecting while the app tracks the mouse, and only stop the copy.** Leaves a highlight that does not match the app's own selection, and a double click that selects twice.
- **A modifier other than Shift (Alt, or Fn/Option as Terminal.app and iTerm2).** Alt-click is reported to apps since ADR 049, and Option-click is how macOS users move the cursor in some apps; Shift is the one bypass shared by Ghostty, kitty, WezTerm, xterm, Windows Terminal and VS Code.
- **Show the browser menu over a tracking app.** The app also acts on the right button, so both react to one click.
- **A webtty-drawn menu (`"webtty"`).** Wanted later; there is nothing to put in it yet. `rightClickAction` is where it plugs in.
- **Change the default to `"copyPaste"` on Windows.** Keeps one default everywhere; documented instead.
