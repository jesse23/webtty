# ADR 068: scroll-benchmark — App modes and scroll behaviour, measured

**SPEC:** [scroll-benchmark](../specs/scroll-benchmark.md)
**Status:** Accepted
**Date:** 2026-10-15

---

## Context

Scrolling through pi blinked. Two fixes came out of it: holding painting during an app's synchronized update ([ADR 067](067.client.synchronized-output.md)), and keeping a scrolled-back view on its text when output arrives ([ADR 066](066.client.output-keeps-scrolled-view.md)). Both pi and Claude Code also offer two modes, and the question was which to run in webtty and what webtty should support:

- **Fullscreen** (pi's default since 1.0; Claude Code's default for new users, `/tui fullscreen`, `CLAUDE_CODE_NO_FLICKER=1`): the alternate screen, the app tracks the mouse and scrolls its own view by lines.
- **Classic** (pi `--tui-mode regular`, Claude Code `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN=1`): the normal screen; webtty's own scrollback scrolls, pixel by pixel.

What was known, besides the measurements below:

- **Where the apps are heading.** pi made fullscreen the default in 1.0.0 and has added only fullscreen features since (search, selection, scrollbar, jump to latest; pi-coding-agent `CHANGELOG.md` and `docs/settings.md`). Claude Code makes fullscreen the default for new users and always renders agent-view sessions fullscreen; classic is not deprecated (code.claude.com/docs/en/fullscreen).
- **Classic reprints.** pi regular clears the screen and the scrollback and reprints the whole transcript on every width change, most height changes and some updates (`tui-main-screen.js`, `ESC[2J ESC[H ESC[3J`). Claude Code classic replays its history on resize, with open reports of duplicated output (github.com/anthropics/claude-code/issues/98411 and 100728). webtty resizes the PTY on every browser resize and zoom, and a long transcript also outgrows the 10,000-line scrollback.
- **What fullscreen costs.** Scrolling moves by the app's lines. Selection and search are the app's own; Shift-drag still gives webtty's selection, and Cmd+F does not see the conversation.
- **Other programs.** vim (9.1+, when the terminal reports mode 2026), neovim (`termsync`, on by default), yazi, fzf, btop, lazygit, zellij and herdr wrap their redraws in synchronized updates; all run on the alternate screen. Only normal-screen output gains from ADR 066: shells, `tail -f`, build logs, `less -X` (git's pager), fzf's inline mode and the classic modes.
- **Other terminals.** Synchronized output with a timeout is near universal (Ghostty, foot, iTerm2 and xterm.js 1 s; kitty 2 s; Alacritty 150 ms; Windows Terminal ~100 ms), and no terminal makes the timeout a setting. Keeping a scrolled view on output is the default everywhere but xterm (Ghostty `scroll-to-bottom = keystroke, no-output`, kitty, WezTerm, Alacritty, xterm.js, gnome-terminal); a key returns to the bottom. The timeouts and defaults are from each terminal's source and documentation (Ghostty `termio/Thread.zig` and its config reference, kitty `screen.c`, alacritty/vte `ansi.rs`, foot `terminal.c`, xterm.js PR 5453, the xterm manual, gnome-terminal's schema).

The scroll benchmark ([SPEC](../specs/scroll-benchmark.md)) measured four builds (neither fix, each alone, both) on ten scenarios with a trackpad, a mouse wheel and a TrackPoint:

- **Blinks.** Before either fix, pi fullscreen and Claude Code fullscreen blink with every input (up to 1.5 and 6 frames a run; up to 6.5 and 7.5 with only ADR 066). With both fixes, 0 for every app and input; with ADR 067 alone, 0 except one blink in two runs of Claude Code fullscreen with a TrackPoint. No other scenario ever blinked.
- **Smoothness.** In the classic modes webtty paints 111 times a second with a trackpad, moving 1.5 px a frame; fullscreen apps paint about 11 times a second, a line (14 px) at a time, with or without the fixes, except for the torn frames ADR 067 removes. With a wheel or a TrackPoint both modes glide, classic in 13–31 px frames and fullscreen in the app's lines.
- **The kept view.** While output streams, a scrolled-back view is pulled to the bottom on almost every frame without ADR 066, and never at rest with it, for all three inputs.
- **Back-to-back updates.** ADR 067's first version starved Claude Code fullscreen, which sends updates 1 ms apart, of paints (7 a second with a TrackPoint, in a run before the reference run). Painting an update as it ends after a held frame, as Ghostty's renderer wakes, reduced that: 9.1–9.5 paints a second against 12.1–12.7 without the hold, with longer gaps (267–417 ms against 188–204 ms at the 90th percentile) and no torn frames. Holding still costs a fast TrackPoint scroll in Claude Code some smoothness.

## Decision

1. **Run pi and Claude Code in fullscreen.** It is where both apps are going, it is blink-free in webtty with ADR 067, and it avoids classic's reprint on every resize and zoom. Classic stays fully supported, also blink-free, as the choice when native scrollback, search and copy matter more. webtty does not configure the apps or wrap their commands: the mode is the app's setting.
2. **Keep ADR 066 and ADR 067 always on, with no setting.** Both are what Ghostty and almost every other terminal do. ADR 067 changes nothing for apps that do not use synchronized output, and ADR 066 changes nothing on the alternate screen. A switch would be code nobody needs, and turning either off only brings a fault back: blinks, or a view pulled to the bottom.
3. **One behaviour for every input device.** The trackpad, the mouse wheel and the TrackPoint go through the same hold, paint and kept-view paths; ADR 045 only paces them differently. The benchmark plays all three, and ADR 066's tests drive each through output mid-glide.
4. **The scroll benchmark is the reference.** A change to scrolling, painting, the wheel or the write path is measured with `bun run bench:scroll` against the build before it, on the SPEC's scenarios and all three inputs, and its numbers go in the change's ADR.

## Considered Options

- **Recommend classic for its smoothness.** Classic scrolls by pixels at the display's rate, about ten times as often as fullscreen with a trackpad. Rejected as the default: it reprints the transcript on every resize and zoom in webtty, both apps develop fullscreen, and fullscreen is blink-free now.
- **Set the apps' modes from webtty** (an env var such as `CLAUDE_CODE_DISABLE_ALTERNATE_SCREEN` in webtty's config, a wrapper for `pi`). Tried and rolled back: it surprises users who chose a mode, and the shell in a webtty session is not the one the wrapper was written for.
- **Make ADR 066 and 067 configurable** (Ghostty's `scroll-to-bottom`, a sync timeout). Not now: no terminal offers the timeout, the scroll rule's default is the industry's, and no one has asked. A setting can be added on a real request.
- **Drop ADR 066 to keep the write path simple.** Rejected: for normal-screen output (shells, logs, classic modes) the difference is the whole problem, a view yanked down on every redraw, and every major terminal but xterm keeps the view.

## Consequences

- With both fixes, no measured app blinks with any input, and a scrolled-back view holds still while output streams.
- Users who prefer classic modes get pixel-smooth scrolling and native selection and search, and the reprint on resize that comes with them.
- Fullscreen apps scroll by their own lines; webtty cannot smooth that. Their scroll speed is the app's setting (pi `fullscreenWheelScrollLines`, Claude Code `CLAUDE_CODE_SCROLL_SPEED`).
- The benchmark needs a running Chrome and a few minutes per scenario; the numbers vary with machine load, so builds are compared in the same run, and blinks are checked against `--dump`'s frames before they are believed.
- Measuring also found a server fault: deleting a session sent SIGTERM, which an interactive shell ignores, so its apps kept running. The server now sends SIGHUP.
