# ADR 060: client — A composition root and feature modules

**SPEC:** [architecture](../specs/architecture.md), [client](../specs/client.md)
**Status:** Accepted
**Date:** 2026-10-14 (root order, ClientEnv and per-socket ack revised after review)

---

## Context

`src/client/index.ts` (565 lines) is a top-level-await script. It loads the config and the wasm, builds the terminal, fits it, runs the WebSocket lifecycle and its close-code policy, and wires about fifteen features: replay, kitty graphics, OSC 52 clipboard writes, the tab title and bell, desktop notifications, the find bar, configured key bindings, Ghostty's shortcuts, font zoom, paste, clear screen, the wheel and smooth scroll. Its problems:

- **Nothing in it can be imported**, so none of that logic is tested: the binding matcher, the zoom clamp, close-code handling and reconnect, the per-message pipeline order, the on-open sequence, paste routing, shortcut dispatch.
- **Order is behaviour, written only in comments.** The configured-binding `keydown` listener must be registered before the shortcut listener, both capture listeners on the container, and both before the InputHandler's; the shortcut listener calls `findBinding` again to skip claimed combos. The shortcut listener uses `findBar` and `clearScreen` declared below it; the graphics `send` closure reads `ws`, assigned later.
- **Six copies of the send guard** (`ws && ws.readyState === WebSocket.OPEN`) and no connection object.
- **Listeners with no teardown**: three `visibilitychange` listeners, five window capture listeners, and `Composer` and `KittyGraphics` install listeners and rAF loops in their constructors.
- **Neighbouring modules mix concerns**: `kitty.ts` (384 lines) holds a stream splitter, a protocol parser, reply encoding, PNG sniffing, cell geometry and a control scanner; `graphics.ts` (662) holds the image store, codecs, placements, command routing and the overlay renderer; `find-bar.ts` mixes pure helpers with its DOM widget.

## Decision

### Feature modules

Each user-facing behaviour is a folder under `src/client/features/` holding its objects and one installer, `<name>-feature.ts`:

```ts
export interface Disposable { dispose(): void }
export function installTabTitle(ctx: ClientContext, deps: TabTitleDeps): TabTitleFeature // extends Disposable
```

- `ClientContext` carries what every feature may use: `term`, `container`, `config`, `terminalTheme`, `mac`, `doc`, `win`. `startClient` takes a `ClientEnv` (`app/browser-env.ts`) holding every global it touches, including the engine loader and the terminal constructor as factories, so the whole root runs on fakes.
- `deps` carries the handles of other parts the feature needs (the connection, the fitter, the find bar, `clearScreen`), passed explicitly by the root. A feature that others need returns a small API next to `dispose` (the layout feature returns `{ fit, schedule }`).
- An installer only wires: it registers listeners through `listen()` into a `DisposableStore` and calls objects that hold the logic. Its `dispose()` removes everything it added and is idempotent.
- Features never import each other.

Infrastructure that is not a feature has its own folders: `app/` (the root, context, config loader, terminal options, platform helpers, the browser environment adapter), `connection/` and `layout/`.

### The composition root

`app/start-client.ts` exports `startClient(env)`, which runs the thirteen steps listed in the SPEC, in today's order (the SPEC lists every listener per target and phase, and the two moves with why each is equivalent), as straight-line code with numbered comments, and returns one disposer that disposes every feature in reverse order. `index.ts` keeps the top-level `await` (so a failure still leaves the page blank, as today) and does nothing but `await startClient(browserEnv())`. A test runs `startClient` on fakes and records each listener's target, type, phase and position, so a change of order fails a test, not a user.

### One key dispatcher

The binding listener and the shortcut listener become one container capture `keydown` listener (`key-dispatcher.ts`), registered where the first one is today. As a capture listener it runs after the vendored `Terminal`'s own container capture `keydown` (added in `open()`) and before the InputHandler's bubble listener, as both do today. When a configured binding matches it does what the binding listener does (`preventDefault`, `stopPropagation`, scroll to the bottom and send its chars when the socket is open) and returns; otherwise it runs the shortcut commands with today's `stopImmediatePropagation` and `performable` rules. This is equivalent: `stopPropagation` never stopped the second listener on the same node, which is why that listener re-checked the binding. A case-by-case test compares the dispatcher with the old pair (binding, empty binding, each shortcut with the find bar open and closed, performable with nothing to do, paste with and without the clipboard API). Font zoom stays a separate window capture listener so it works without focus, and still calls `fit()` synchronously.

Shortcut actions go through a **command map** (`shortcut-commands.ts`): action → handler returning whether it was done, so dispatch is a table lookup and each command is tested alone.

### PtyConnection

`connection/pty-connection.ts` owns the WebSocket: the URL (`cols`, `rows`, `flow=1`), connect, the close-code policy (`close-policy.ts`, pure: 4003 resets the terminal and reconnects at once, 4001 and 1001 close the tab, anything else retries after 2 s), status lines (`status-line.ts`, pure), and one `send` with the single open guard. It takes the `WebSocket` constructor and timers by injection. Hooks that must run before any message (`replay.connected()`, `clipboard.connected()`) are called synchronously when the socket is created; on open it calls `graphics.reset()`, sends the size and calls `resyncFocus()`, in that order. Each socket gets its own `OutputAck`, bound to that socket's `send` with today's per-socket open check, and disposed in that socket's `onclose` before any reconnect (the immediate 4003 one included), so an ack queued for a closed socket is never sent on its successor.

### The output pipeline stays a direct call sequence

`output-pipeline.ts` builds the per-message handler once: `replay.output` → `graphics.feed` → `replay.parsed` → `ack.parsed` → `smoothScroll.onOutput`. No event bus, no array of subscribers to iterate, no allocation per message; a test pins the order. The ack still follows the parse (ADR 048).

### Splits of the existing modules

- `ack.ts` → `connection/output-ack.ts`, `replay.ts` → `connection/replay-window.ts`, `fit.ts` → `layout/fit-insets.ts`, `edge.ts` → `layout/edge-rects.ts` + `layout/edge-extender.ts`, `theme.ts` → `app/terminal-theme.ts`, `shortcuts.ts` → `features/keyboard/shortcut-map.ts`, `clipboard-write.ts` → `features/clipboard/clipboard-writer.ts`, `compose.ts` → `features/compose/composer.ts`.
- `notifications.ts` → `desktop-notifier.ts` (policy) + `browser-notifications.ts` (adapter and `activates`).
- `find-bar.ts` → `find-bar.ts` (view, takes `document`) + `find-format.ts` + `find-keys.ts`.
- `wheel-stream.ts` → `wheel-classifier.ts` (with the VS Code MIT notice) + `wheel-stream.ts`; `smooth-scroll.ts` → `smooth-scroll.ts` + `scroll-split.ts`.
- `kitty.ts` → `features/kitty/protocol/` (seven files by concern); `graphics.ts` → `features/kitty/graphics/` (`image-store`, `image-decoder`, `placements`, `kitty-limits`, `overlay-canvas`, and the `kitty-graphics` facade whose `feed` hot path is unchanged).
- The terminal-canvas selectors are named once in `layout/terminal-canvas.ts`, keeping each call site's exact string (unifying them would change which canvas some sites find).
- `Composer`, `EdgeExtender` and the kitty overlay gain an idempotent `dispose()`. Nothing calls it at runtime except the root's disposer, which a page never runs, so behaviour does not change.

## Considered Options

- **An event bus between features.** Rejected: it hides who reacts to what, and on the per-message path it adds a fan-out and allocations.
- **A command registry resolved by name at run time.** Rejected in favour of explicit handles: the root already knows every feature, and passing handles keeps every dependency visible in one file and checked by `tsc`.
- **Keep two key listeners, ordered by registration.** Workable, but the ordering contract stays implicit; one dispatcher states it in code, and the equivalence test proves nothing changed.
- **A UI framework.** Rejected (ADR 059).

## Consequences

- `index.ts` drops to about 15 lines; the wiring is testable and tested.
- Each feature can be read, tested and removed alone; a new feature is a folder and one line in the root.
- The order that matters is in one file and pinned by tests.
- About 2,500 lines move; the moved modules' tests move with them, and `index.ts` imports are updated in each step.
