# ADR 039: client — Follow devicePixelRatio changes

**SPEC:** [client](../specs/client.md)
**Status:** Accepted
**Date:** 2026-10-12

---

## Context

ghostty-web's `CanvasRenderer` reads `window.devicePixelRatio` once in its constructor and sizes the canvas backing store (`cols × cellWidth × dpr`) from that value for the rest of the page's life. Moving the window to a monitor with a different scale (Retina ↔ external display) or changing browser zoom changes the ratio, but the renderer keeps the old one: text renders blurry or mis-scaled until the page is reloaded.

The canvas' CSS size does not change when only the ratio does, so the container `ResizeObserver` does not fire, and the window `resize` that does fire runs `fit()`, which sees the same cols and rows and does nothing (ADR 033).

## Decision

Watch `matchMedia('(resolution: <dpr>dppx)')`. When it stops matching, write the new `window.devicePixelRatio` into the renderer's (private) `devicePixelRatio`, remeasure the font, force a full render, schedule a fit, and re-arm the query for the new ratio. The forced render sees that the backing store no longer matches `cols × cellWidth × dpr` and resizes and repaints the canvas itself, the same self-correction ADR 031 relies on.

## Consequences

- Moving between displays of different scale keeps text crisp without a reload.
- Depends on a private field of ghostty-web's renderer; an upgrade that renames it would silently drop the fix (the cast compiles either way).
- Does not address fractional ratios (browser zoom other than 100%, Windows 125%/150%): ghostty-web compares the integer backing width against an unrounded `cols × cellWidth × dpr`, so it resizes and clears the canvas on every frame. That needs a fix inside ghostty-web.
