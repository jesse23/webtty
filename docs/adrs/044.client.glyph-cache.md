# ADR 044: client — Glyph cache for full repaints (rejected)

**SPEC:** [client](../specs/client.md)
**Status:** Rejected
**Date:** 2026-10-13

---

## Context

ADR 043 made scrolling draw only the rows that come into view, but a full repaint still draws every cell with `fillText`. Full repaints happen on output that scrolls the screen (every row is dirty), a resize, a font, theme or ratio change, and the scrollbar fade-out. At 175×64 cells that is about 11,000 `fillText` calls, each after setting `font` and `fillStyle` from strings built for that cell.

A glyph cache is the usual answer: draw each distinct glyph once into an offscreen atlas canvas and copy it into place with `drawImage`. It must leave the canvas exactly as `fillText` does.

## Decision

Do not add a glyph cache. The renderer keeps drawing every glyph with `fillText`.

In Chrome, a full repaint from the cache took about twice the script time and twice the GPU-process time of `fillText`, even though over 98% of the glyphs came from the cache (Measurements). Chrome already caches shaped runs and rasterised glyphs behind `fillText`, and one `fillText` costs less than one `drawImage` from another canvas. The cache also failed the exactness check: `measureText` placed the ink of some combining marks inside the cell when it was not.

### The design that was measured

- **A tile is the whole cell: the glyph drawn over its background.** A glyph drawn alone on a transparent atlas and blended into place has its premultiplied edges rounded to 8 bits one extra time, so its edges can differ from `fillText` by a level. So the atlas held the cell's opaque background with the glyph drawn over it, exactly as the row draws it: `font`, `fillStyle`, faint `globalAlpha`, and the alphabetic baseline at the cell's baseline. Copying an opaque tile onto whole device pixels gives the cell the same pixels as `fillText` over that background.
- **Key:** the font string (bold, italic, size, family), the foreground and background CSS colours, faint, the cell width (1 or 2) and the grapheme string. Selection colours and inverse are just other colours. The ratio, font and metrics are fixed for the atlas' life.
- **When a tile is used:** only when all three of these hold:
  - The glyph's ink box (`actualBoundingBox*` from `measureText`, measured once per key) lies inside the tile.
  - The background is opaque. A translucent theme background would be blended twice.
  - No glyph drawn earlier in the row reaches into the cell. The tile would erase that ink, and a full redraw keeps it under this glyph.

  Glyphs that overflow their cell (italic overhang, colour emoji, tall combining stacks) and the cursor's clipped glyph were drawn with `fillText`. The right edge of their ink marked the cells after them as not tileable for the rest of the row. Underlines, strikethrough and link underlines were drawn after the tile, in the same order as before.
- **Bounds:** one atlas canvas of 2048×2048 device pixels, filled cell by cell, with wide glyphs taking two cells. A full atlas was cleared and filled again. The atlas was also cleared when the ratio, font or metrics changed.

The implementation is not kept. It was a change to `renderer.ts` only (`drawTile`, `addGlyph`, `drawAtlasTile`).

## Measurements

Apple M3 Pro, headless Chrome 155 (ANGLE Metal), 1400×900 (175×64 cells), Menlo 13 px. The two builds ran side by side: the build before this ADR, and the same build with the cache.

**Full repaints.** The page had the same output in both builds. "Typical" is `git log --stat --color` plus TypeScript source. "Mixed" is the generator used in ADR 043: truecolor and 256-colour runs, styles, emoji with VS16, ZWJ sequences, flags, combining marks, CJK and box drawing. Each run forced 60 full repaints, one every other frame (a `contextrestored` event, which resizes the canvas and repaints every row). The table shows the script time of the repaint frame and the GPU process' main-thread busy time (from a trace) per repaint. The atlas was already filled before the 60 repaints.

| Per full repaint | `fillText`: script / GPU | Cache: script / GPU | `fillText` calls, before → with the cache |
|---|---|---|---|
| Official, DPR 2, typical (two runs) | 6.6 / 3.6 ms | 14.7–15.5 / 8.8–9.1 ms | 11,200 → 201 |
| Official, DPR 2, mixed | 8.4 / 4.8 ms | 13.4 / 8.7 ms | 10,883 → 1,151 |
| Coder, DPR 2, typical | 8.6 / 4.0 ms | 13.5 / 8.0 ms | 11,200 → 201 |
| Coder, DPR 2, mixed | 7.8 / 4.4 ms | 13.9 / 8.7 ms | 10,915 → 1,191 |
| Official, DPR 1, typical | 8.4 / 3.9 ms | 13.3 / 7.7 ms | 11,200 → 201 |

A variant that built the key and looked up the tile for each cell, but still drew with `fillText`, took 9.1–9.9 ms of script and 3.6 ms of GPU time on the first row. Of the extra script time, about 3 ms is the per-cell key and lookup. The other 5 ms, and all of the extra GPU time, is `drawImage` instead of `fillText`. A cheaper key would not close the gap.

**Raw call cost.** This was measured on a standalone page with the same Chrome and font, over 20,000 calls, best of 5:

- One `fillText` with `font` and `fillStyle` set took 0.31–0.36 µs. That held for ASCII, CJK, colour emoji (including ZWJ and flags), combining sequences, Devanagari and box drawing alike.
- One 9-argument `drawImage` from an atlas canvas took 0.54–0.57 µs.
- A 175×64 grid drawn per cell took 4.1 ms with `fillText` and 10.1–11.7 ms from an atlas. The GPU process time was 5.2 and 7.0 ms per frame. The atlas source (a canvas, an `ImageBitmap` or an `OffscreenCanvas`) did not change this.
- One `ImageBitmap` per glyph, drawn with 3-argument `drawImage`, took 10.7 ms of script and was slower on the GPU.

**Whole-app scenarios.** Streaming output, 20 resizes and wheel scrolling by lines and pages were slower with the cache in every run. These numbers vary from run to run more than the full-repaint numbers do: line scrolling took 1.2–3.1 ms per drawn frame without the cache and 4.1 ms with it.

**Exactness.** Screenshots of both builds at the bottom, scrolled up 7 lines, and with a selection were compared on the mixed output. On the official engine at DPR 2, 82 device pixels differed, by up to 46 levels, at every scroll position. All of them were at combining marks (`é`, `ä`, `ñ` as base plus mark): `measureText`'s `actualBoundingBoxAscent` put the mark inside the cell, but it reaches into the row above. A full redraw keeps that ink in the row above (ADR 043's joined rows), and the tile cut it off. The Coder engine at DPR 1 differed by up to 19 levels. A safety margin on the ink box would send more glyphs back to `fillText`, including full-height box drawing and block elements, which touch the cell's edges. That would make the cache slower still.

`scrollbench` (Bun, recording fake canvas) is not a fair comparison here. Its `drawImage` and `fillText` are both free, so it only counts calls.

## Considered Options

- **A transparent atlas, with tiles blended over the drawn background.** Fewer keys, because the background is not part of the key. But this is not exact: it rounds the glyph's premultiplied edges one extra time. It would cost the same `drawImage` per cell.
- **Separate small canvases or `ImageBitmap`s per glyph**, drawn with 3-argument `drawImage`. This was measured too, and it was slower.
- **Not tested, and neither decided here.** Leaving the measured gap as it is:
  - Skipping `font` and `fillStyle` assignments that did not change: about 10% of the standalone grid's script time (4.1 → 3.7 ms).
  - One `fillText` per run of cells with the same style: far fewer calls. But it places glyphs at the font's advance instead of at each cell, so it is not exact for fonts whose advance is not a whole cell.

## Consequences

- Full repaints keep their current cost: about 6.6–8.6 ms of script per 175×64 repaint in headless Chrome, plus 3.6–4.8 ms in the GPU process.
- Chrome's own glyph caching behind `fillText` is what a cache has to beat. Before another attempt at a cache, measure raw call cost and an exactness check first.
- These measurements are from headless Chrome on macOS only. Firefox and Safari were not measured, and their `fillText` and `drawImage` costs may differ.
