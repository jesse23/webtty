# ADR 034: Client — configurable `padding` around the terminal canvas

**SPEC:** [client](../specs/client.md)
**Status:** Accepted
**Date:** 2026-09-21

---

## Context

[ADR 033](033.client.padding-fit.md) removed the 15px scrollbar reserve so the strip
around the canvas is only the sub-cell remainder, and added `theme.padding` to colour it.
That gives no way to ask for breathing room: the canvas always runs to the edge of the
browser tab, which some users prefer to avoid. Terminal emulators such as Ghostty and
Windows Terminal expose a padding setting for this.

## Decision

Add a top-level config key, `padding`: a non-negative number of CSS pixels reserved on
all four sides of the canvas, default `0` (no change for existing configs). Invalid values
(negative, non-numeric) fall back to `0`. It is served to the client through
`GET /api/config`.

The client subtracts twice the padding from each container dimension before computing
cols and rows, so the padding is reserved out of the same space the sub-cell remainder
comes from. The leftover space is then distributed as follows: the top and left edges are exactly
`padding`, and the leftover, less than one cell, goes to the right and bottom. So `padding`
alone decides the gap at the top and left, and `0` puts the terminal flush against the
browser toolbar and the left edge. Centring the leftover left a thin strip at the top and
left in a different colour from a full-screen app's edge cells, where it was very visible. The space set by `padding` is coloured by the container
background, `theme.padding` if set and `theme.background` otherwise, so the colour needs no new
setting. The leftover strip is not coloured by it: [ADR 035](035.client.edge-extend.md)
extends the edge cells' own background into it.

## Considered Options

### Option A: One `padding` number for all sides (chosen)
Simple and predictable, and matches the way the strip is already coloured and centred.

### Option B: Separate horizontal and vertical (or per-side) padding
More control, but more keys and validation for a case nobody has asked for yet. Can be
added later if needed.

### Option C: Percent or cell-based padding
Cells would keep the grid aligned but make the size depend on the font. Rejected in favour
of plain pixels.

## Consequences

**Positive**
- Users can add breathing room, and colour it to match their theme or app.
- Default `0` keeps existing behaviour.

**Negative**
- `theme.padding` (a colour) and `padding` (a size) share a word. They are in different
  places (inside and outside `theme`), and the colour key is documented as the colour of
  the padding, but they are easy to confuse.
- The leftover, up to one cell, now shows on the right and at the bottom instead of being
  split around the canvas. With `theme.padding` set to a sidebar colour it may show as a dark
  strip beside or under lighter cells; setting `theme.padding` to the app's main colour hides
  it when `padding` is `0`.
