# ADR 056: client — Desktop notifications from OSC 9 and OSC 777

**SPEC:** [client](../specs/client.md), [config](../specs/config.md)
**Status:** Accepted
**Date:** 2026-10-14

---

## Context

Programs ask their terminal for a desktop notification with one of two sequences:

- **OSC 9** (iTerm2): `ESC ] 9 ; <body> BEL` (or ST). No title. Claude Code, build tools and shell hooks (`printf '\e]9;done\a'`) send it.
- **OSC 777** (rxvt-unicode's `notify` extension, also Ghostty's and foot's): `ESC ] 777 ; notify ; <title> ; <body> BEL`.

webtty showed neither: the sequences reached the engine and stopped there.

OSC 9 is shared. ConEmu uses `OSC 9 ; <n> ; ...` for other things: `9;4` is the progress report (`9;4;1;50`), and `9;1` to `9;12` are sleep, a message box, the tab title, wait for input, a GUI macro, run a process, an environment variable, the working directory, xterm emulation, a comment and a prompt mark. Ghostty's parser (`src/terminal/osc/parsers/osc9.zig`, at the pinned commit `05dcf887`) tries the ConEmu forms first and takes `OSC 9` as a notification only when the payload is none of them: `9;4;1;50` is a progress report, `9;42 tests passed` and a bare `9;4` are notifications. OSC 777 (`rxvt_extension.zig`) takes only the `notify` extension and needs both fields: `777;notify;<title>;<body>`, the body running to the end (it may hold `;`), the title possibly empty. Other extensions, and `notify` without a second `;`, are dropped. Kitty's OSC 99 is a separate command that does not reach this callback.

Ghostty's official libghostty-vt reports both to the embedder. `GHOSTTY_TERMINAL_OPT_DESKTOP_NOTIFICATION` (`include/ghostty/vt/terminal.h`) takes a `GhosttyTerminalDesktopNotificationFn(terminal, userdata, const GhosttyTerminalDesktopNotification*)`, called synchronously during the write, with a sized struct holding a `title` (empty for OSC 9) and a `body`, both borrowed for the callback's duration. NULL, the default, ignores the requests. Option and struct are in the wasm's `ghostty_type_json` manifest, as the options the binding already sets are. So no scanner of our own is needed: Ghostty's parser does the disambiguation, chunk boundaries and size limits.

Ghostty the app, the embedder webtty follows:

- **Config.** `desktop-notifications` (default `true`): "applications running in the terminal can show desktop notifications using certain escape sequences such as OSC 9 or OSC 777". Off, `Surface.zig` logs and drops them.
- **Rate limit.** `Surface.showDesktopNotification` shows at most one notification a second, and the same title and body at most once in five seconds.
- **When it shows (macOS).** The app posts every notification but presents it only when `!window.isKeyWindow || !surface.focused` (`shouldPresentNotification`): nothing appears while the user is looking at the terminal that asked. Notifications are removed when the surface gains focus; clicking one brings its window forward and focuses the surface. The notification's title is the program's title, its subtitle the surface title. On first use the app asks the system for permission (`requestAuthorization`), and shows nothing until it is granted.
- **GTK** shows them focused or not, with `Ghostty` for an empty title, and uses the body as the notification id, so the same body replaces the earlier one.

The browser has its own rules. The Notification API exists only in a secure context (https, or localhost). Permission is `default` until asked, then `granted` or `denied`, per origin. Firefox and Safari grant the prompt only from a user gesture, and Chrome demotes prompts that come without one to a quiet icon in the address bar; a prompt on page load is the pattern browsers penalise. Chrome on Android throws from `new Notification()` (pages must use a service worker), and iOS Safari has no Notification API outside home-screen web apps.

And, as for the bell and OSC 52 (ADR 052, ADR 053), the server replays the session's recent output on every connect. A notification in that history would pop up again on every reload and reconnect.

## Decision

### Take them from libghostty-vt's callback

The binding (`ghostty.ts`) installs a `DESKTOP_NOTIFICATION` callback when the terminal is created with the new `GhosttyTerminalConfig.desktopNotifications` on (default true), and leaves it NULL otherwise. The callback checks the struct's `size` covers `body`, copies `title` and `body` out as UTF-8 (invalid bytes become U+FFFD), and queues them. `readEffects` gains `notifications`, every request since the previous call in order (two in one write are two notifications). `Terminal` gains the `desktopNotifications` option, passed to the engine, and `onDesktopNotification({ title, body })`, fired for each.

### Show them as Ghostty on macOS does

`DesktopNotifier` (`src/client/notifications.ts`) decides what happens to each, in this order:

1. **Replayed ones are dropped.** The replay's end is found as for bells (ADR 053): from each connect, output is replay through the first message shorter than the server's piece, or until a 1 s pause. That logic moves out of `TabTitle` into `ReplayWindow` (`src/client/replay.ts`), which `index.ts` feeds and both consult. Not held until input as OSC 52 writes are: like the bell, a notification is for a tab the user is away from, so after a reconnect in the background (laptop wake, server restart) it must still arrive.
2. **Rate limited** as Ghostty does: one a second, and the same title and body once in five seconds, per tab.
3. **Nothing while the terminal is focused.** Focus is ADR 053's: the window has focus and keyboard focus is in the terminal. In another tab, another window or another app, or with focus in the address bar, it shows. This is Ghostty on macOS. Not `document.hidden`: a visible tab in a window behind another app is as unattended as a hidden one, and visibility misses it.
4. **Shown with `new Notification(title, { body, tag })`** when permission is `granted`. The title is the program's title, or for OSC 9 (no title) the tab's name: the program's OSC 0/2 title, or the session id. `tag` is the session, title and body, so two tabs on one session, or a repeat after the rate limit, replace one notification instead of stacking (GTK's body-as-id). Title and body go to the API as plain text; nothing is parsed as HTML. Clicking it focuses the window and the terminal and closes it; the terminal gaining focus or a key in the tab closes every notification it showed, as Ghostty removes them on focus.
5. **Otherwise, the bell mark.** With permission not granted, no API (http, iOS Safari) or a constructor that throws (Chrome on Android), the tab title gets the bell's `🔔 ` (ADR 053) until the terminal is attended. It is the bell's mark, so `bellTitle: false` turns it off too.

### Ask for permission on the next input after the first notification

Never on page load. The first notification that arrives (live, focused or not) while permission is `default` arms the request, and the next `keydown` or `mousedown` in the tab that activates the page calls `Notification.requestPermission()` from that event, a user gesture in every browser. Esc and keys the browser reserves do not activate the page (HTML's activation-triggering input events), and a request from one is refused or demoted, so such a key leaves the request armed for the next: `navigator.userActivation.isActive` decides, and where it is missing only Esc is passed over. It is asked once per page load: a dismissed prompt is not repeated until a reload, and `denied` is never asked again (the browser would not show it). The notification that armed it is not shown afterwards: by then the user is in the tab. Ghostty asks the system on first use too; the gesture is what the browser adds.

### Config

`desktopNotifications` (boolean, default `true`, Ghostty's `desktop-notifications`), served by `/api/config` and read on every tab reload. `false` leaves the callback unset, so Ghostty ignores OSC 9 and OSC 777 and webtty never asks for permission.

## Consequences

- `printf '\e]9;done\a'`, `printf '\e]777;notify;Build;passed\a'`, and Claude Code's terminal notifications show as desktop notifications while the user is elsewhere, once permission is granted. Clicking one returns to the tab.
- The first notification of a page shows only as `🔔 ` in the title; the browser's permission prompt comes with the next key or click in the tab. A user who never interacts with the tab is never asked.
- ConEmu's progress reports (`9;4`) and the other `9;<n>` forms do not notify, as in Ghostty. They are not shown in any other way either.
- Reloads and reconnects do not notify for history. As for bells (ADR 053), a notification in the first live message after a replay that ends on a full piece is taken as replay unless it comes 1 s later, and a replay piece delayed by 1 s or more can let a replayed one through.
- Over plain http (not localhost) notifications are never shown; the bell mark is.
- A program can notify the user without asking, as in Ghostty's default; `desktopNotifications: false` turns that off.

## Considered Options

- **libghostty-vt's callback (chosen).** The parser that already runs, with Ghostty's own OSC 9 / ConEmu split.
- **Scan the PTY stream for OSC 9 / OSC 777 ourselves.** A second parser to keep in step with Ghostty's (ConEmu forms, ST vs BEL, sequences split across messages, size limits), for something the engine already reports.
- **Show only while the tab is hidden (`visibilityState`).** Misses a visible window behind another app, the common case for a notification.
- **Show always, as GTK does.** A banner about the terminal the user is typing in; Ghostty on macOS suppresses it, and the bell mark would do for that case anyway.
- **Ask for permission on page load, or on the first input whatever happens.** Browsers penalise prompts without a reason in view, and a session that never notifies should never ask.
- **Hold until input after a connect, as OSC 52.** Loses every notification after a background reconnect, which is when they matter.
- **Our own in-page toast as the fallback.** Visible only to a user already looking at the tab, who does not need it; the title mark shows in the tab strip.
