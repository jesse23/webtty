# ADR 048: webtty — PTY output flow control

**SPEC:** [webtty](../specs/webtty.md), [client](../specs/client.md)
**Status:** Accepted
**Date:** 2026-10-13

---

## Context

The server broadcasts PTY output with `client.send(data)` for every `onData` chunk, to every client, with no flow control. Nothing ever waits for a browser tab: a PTY that writes faster than a tab parses fills the WebSocket's send buffer without bound.

Under Bun, `import { WebSocketServer } from 'ws'` (ADR 001) does not load the `ws` package. Bun substitutes its built-in shim (`BunWebSocketMocked` over native uWebSockets), and the shim breaks the stream once a client falls behind:

- **Reordering.** Native `send` returns `0` when it drops a message past its 16 MB `backpressureLimit`. The shim then queues that message, but later calls to `send` go straight to native and overtake the queue.
- **Duplicates and gaps.** When the shim drains its queue, it treats `-1` (accepted, with backpressure) as a failure and sends the head message again, while the rest of the queue waits.

`ws` under Node has neither bug. `origin/main` has the same code. Any tab that falls more than 16 MB behind sees it: a background tab, a slow machine, or a heavy truecolor flood (`cat` of a large log, a build). Reproduced on webtty's own server with a client that sleeps 0.5 ms per message: 18,398 backward jumps, gaps, missing lines, and SGR sequences spliced into other lines, which the terminal shows as literal `38;2;…m` text.

Bounding the buffer fixes both problems. The shim misbehaves only past 16 MB, and memory on the server stops growing with the slowest tab.

## Decision

The server paces output to each client by acknowledgements from that client, and pauses the PTY when every client is behind and the PTY can pause.

**Client.**

- Connects with `?flow=1` in the PTY WebSocket URL, which declares that it will acknowledge.
- Counts the characters (UTF-16 code units, `string.length`) of each output message after `graphics.feed()` returns. `term.write()` parses synchronously in the wasm (the vendored `writeQueue` is never filled), so by then the output has been parsed.
- Sends `{"type":"ack","chars":<total>}`, with the running total since connect, every 64 Ki characters, and 100 ms after the last message when less than that is outstanding. A total, not a delta, so a repeated or late ack cannot be counted twice.

**Server (`src/server/flow.ts`, `OutputPacer`, one per session).**

- Per client: characters sent, characters acknowledged, and a queue of pending output.
- Sends output straight through while unacknowledged characters are under the high-water mark (2 Mi characters, at most 6 MB of UTF-8, far under the shim's 16 MB). At the mark the client is *blocked*: new output is queued in order.
- When acks bring the client down to the low-water mark (512 Ki characters), it is unblocked and the queue is sent in order, coalesced into messages of up to 64 Ki characters, until the client blocks again. Whole PTY chunks are joined and never split, so a surrogate pair is never cut.
- Scrollback replay and the banner go through the same path, so they count against the window.
- When every client of a session is blocked and the PTY has `pause()` (node-pty), the PTY is paused and the app blocks on its own writes, as in a real terminal; it resumes as soon as any client is unblocked or leaves. `Bun.Terminal` has no pause or resume (checked on Bun 1.3.11), so under Bun the PTY keeps running while clients are blocked.
- A queue over 16 Mi characters closes that client with `4003` (*fell behind*). Under Bun this is what bounds memory. The client resets its terminal, says so in one status line, and reconnects at once, getting the scrollback replay like a new tab.
- A client that connects without `?flow=1` is *legacy* (a tab loaded before an upgrade): it is sent output straight through as before, and closed with `4003` once `bufferedAmount` passes 8 MB. The old client reconnects on any code other than `4001` and `1001`, so it recovers through the replay. The client is served by the same server, so a mismatch lasts only until that tab reloads.

Frames stay text frames. The URL parameter replaces the brief's "treat a client that has never acked as legacy": the server knows the protocol at connect, before any output, instead of guessing from silence.

## Consequences

- Output reaches every acknowledging client in order, without gaps or duplicates, at any speed, and the server's send buffer per client stays under about 2 Mi characters plus one PTY chunk.
- A hidden tab that stops processing holds its window and its queue. Under node-pty the app is paced by the slowest attached tab, as with tmux or a real terminal on a slow link. Under Bun, a tab that falls 16 Mi characters behind is reset and replayed; what scrolled past in that time is not in its history.
- One small upstream JSON message per 64 Ki characters of output.
- The `ws` shim stays in use under Bun. Its bugs are no longer reachable for acknowledging clients; a legacy client can still hit them between 16 MB of native backlog and the 8 MB `bufferedAmount` check (the shim only counts what it queued), until it reloads.

## Considered Options

- **Native `Bun.serve` WebSockets with our own queue.** Fixes the shim at its source and exposes `getBufferedAmount()`, but replaces the `node:http` + `ws` server that also has to run on Node (Windows, `server:node`), so it means two WebSocket server paths. It still needs a bound on per-client memory, which takes acknowledgements or a buffer cap anyway.
- **Stopgap: close a client when `bufferedAmount` grows.** Small, but the shim's `bufferedAmount` is 0 until native has dropped a message, so it cannot see trouble coming; every slow tab would be disconnected and replayed rather than slowed down, and the app is never paced.
- **Do nothing.** Background tabs and heavy output keep corrupting the screen under Bun, and server memory grows with the slowest tab.
