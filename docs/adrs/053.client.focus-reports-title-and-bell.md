# ADR 053: client — Focus reports, the app's title and the bell

**SPEC:** [client](../specs/client.md), [config](../specs/config.md)
**Status:** Accepted
**Date:** 2026-10-14

---

## Context

Three things a program asks of its terminal reached webtty's engine and stopped there:

- **Focus reports (DEC mode 1004).** Neovim and tmux (`focus-events on`) turn the mode on to hear `CSI I` when the terminal gains focus and `CSI O` when it loses it: Neovim runs `FocusGained` (`autoread` checks files then), tmux passes it to the active pane. webtty never sent either, so `:checktime` on focus never ran and tmux's own focus events were dead.
- **The title (OSC 0 / OSC 2).** `Terminal.onTitleChange` fires with the title Ghostty parsed (ADR 042, ADR 047), but `index.ts` set `document.title` to `<session> | webtty` once and never listened. Every webtty tab read the same, whatever ran in it.
- **The bell (BEL).** `Terminal.onBell` fires, and nothing listened. A job that rings when it is done (`make; tput bel`, an agent's terminal-bell notification) was silent.

Ghostty's official libghostty-vt, at the pinned commit (`05dcf887`):

- exports `ghostty_focus_encode(GhosttyFocusEvent, buf, len, out_written)`, which writes `CSI I` (`GAINED`) or `CSI O` (`LOST`); `GhosttyFocusEvent` is in the wasm's type manifest. The terminal itself does nothing for mode 1004 (`stream_terminal.zig`: `.focus_event => {}`); sending the reports is the embedder's job.
- reports the title through `TITLE_CHANGED` and the bell through `BELL`, read after each write (`readEffects`). An empty `OSC 2 ;` sets the title to `''`; RIS does not clear it.

Ghostty the app, the embedder webtty follows:

- **Focus.** `Surface.focusCallback` runs when the surface gains or loses keyboard focus, which includes the window becoming or ceasing to be the key window (another app, another window). `Termio.focusGained` sends the report only while mode 1004 is on. And setting the mode sends the current state at once (`termio/stream_handler.zig`: `.focus_event => if (enabled) messageWriter(.{ .focused = ... })`), so a program that turns it on learns where focus is without waiting for a change.
- **Title.** The window title is the program's title as it is (`computeTitle` in the macOS app), with a 🔔 in front while the bell is active.
- **Bell.** `bell-features` defaults to `attention` and `title` (`system`, `audio` and `border` are off). `title`: "Prepend a bell emoji (🔔) to the title of the alerted surface until the terminal is re-focused or interacted with (such as on keyboard input)". The macOS app sets the surface's bell on every BEL, focused or not, and clears it when the surface gains focus or gets a key down. `attention` bounces the Dock icon while the app is inactive.

webtty has one thing a native terminal does not: the server replays the session's recent output on every connect (ADR 007, ADR 048). A BEL in that history would ring again on every reload and reconnect. The replay is not delimited (ADR 052), but it is sent as one burst: the server queues all of it in its `open` handler, at most 64 Ki characters a message and, at the default `scrollback` (256 KiB, under the 2 MiB high-water mark), without waiting for an acknowledgement (ADR 048).

## Decision

### Terminal focus is keyboard focus in a focused window

The terminal has focus when the browser window has focus and keyboard focus is inside the terminal's container (its textarea, or the container on the way to it). That is Ghostty's surface focus: switching tabs, switching to another app or window, or clicking the address bar or devtools takes it away; coming back gives it back. A tab merely visible behind another window does not have it, as a Ghostty window that is not the key window does not.

`Terminal` follows it with `focusin` and `focusout` on the container. A `focusout` whose `relatedTarget` is inside the container (the padding click that `handleFocusIn` sends on to the textarea) is not a change; a window blur is a `focusout` with no `relatedTarget`, and a window focus a `focusin`. Repeated events with no change send nothing.

### Focus reports are Ghostty's encoder, sent as Ghostty sends them

The binding gains `encodeFocus(focused)` (`ghostty_focus_encode`). `Terminal`:

- on a focus change, sends the report through `onData` if mode 1004 is on;
- after each write, if mode 1004 went from off to on, sends the current state, as Ghostty does when the mode is set. Only the state after the write is compared, so a set that does not change the mode (it was already on), or an off-and-on inside one write, sends nothing; programs set it once when they start.

The replay can turn the mode on, and the report then tells the program this tab's focus. That is the point of the report on set, and it is right for the tab that just connected. With two tabs on one session, each sends its own changes and the last one wins.

### The tab title is the program's title

`TabTitle` (`src/client/tab-title.ts`) owns `document.title`: `<title> | webtty` while the program has set a non-empty title, `<session> | webtty` otherwise (the old title). `index.ts` feeds it `onTitleChange`. A title in the replay is applied: it is state, the title the program last set, not an event. The ` | webtty` suffix stays, so webtty tabs still read as webtty in the tab strip and history.

### The bell marks the title, Ghostty's `title` feature

On a bell, `TabTitle` puts `🔔 ` in front of the title, focused or not, until the terminal gains focus or a key is pressed in the tab, as in Ghostty. A focused tab that rings (a failed Tab completion) shows the 🔔 until the next key; a tab in the background keeps it until the user comes back. Nothing else happens: no sound (Ghostty's `audio` and `system` are off by default, and a page may play sound only after user input), no flash (Ghostty's `border` is off by default), no notification (it needs a permission prompt, as `attention` needs none in Ghostty).

**Bells in the replay are ignored.** After each connect the client treats output as replay until the first gap of 1 s with no output: `TabTitle.connected()` at socket open, `TabTitle.output(now)` before each message is parsed. The first message starts the replay; a message that arrives 1 s or more after the previous one ends it, and its bells and every later one count. The replay arrives as a burst, so a gap means it is over; a program that wrote without a pause since the connect has its bells ignored until it pauses.

### Config

`bellTitle` (boolean, default `true`), served by `/api/config` and read on every tab reload: `false` leaves the title alone on a bell, as Ghostty's `bell-features = no-title`. A boolean rather than Ghostty's feature list: `title` is the only feature webtty has.

## Consequences

- Neovim's `FocusGained` / `FocusLost` and `autoread` on focus, tmux `focus-events`, and focus-aware TUIs work. A program that enables the mode gets `CSI I` or `CSI O` at once.
- A tab that loses focus to the address bar, devtools or a browser dialog sends `CSI O`, as Ghostty does when its window loses key status to a panel.
- Two tabs on one session send interleaved reports; the program sees the latest.
- Tabs read as what runs in them: a shell that sets the title (`user@host: ~/dir`), vim's file name, Claude Code's title. A program that never sets one keeps `<session> | webtty`. A title from an earlier program stays until another is set, as in Ghostty.
- A bell shows as `🔔 ` in the tab title until the user focuses the terminal or presses a key. Reloads and reconnects do not mark the tab for bells already rung.
- A bell less than 1 s after the previous output, while the output has not paused since the connect, is not shown. A replay delayed by a gap of 1 s or more (a link slower than about 0.5 Mbit/s for a 64 Ki message, a stalled connection) can mark the tab for a replayed bell; the mark goes on the next focus or key.

## Considered Options

- **Focus from `document.visibilityState`, or from window focus alone.** Visibility misses a window behind another app, which Ghostty counts as unfocused; window focus alone misses focus moving to the address bar or devtools, and the textarea is the only input in the page anyway.
- **Report only changes, nothing on set.** Ghostty sends the state on set; programs rely on it to start in the right state.
- **Hold bells after each connect until user input, as OSC 52 writes are (ADR 052).** The bell's use is a tab the user is away from; after a reconnect in the background (laptop wake, server restart) every bell would be lost until the user came back.
- **A replay-end marker from the server.** Exact, but a protocol change for every client, rejected for the same reason in ADR 052.
- **Mark only while the terminal is unfocused.** Simpler on the eye, but Ghostty marks a focused surface too, and the next key clears it.
- **Flash the screen, play a sound, or post a notification.** Ghostty's defaults do none of the first two; a notification needs a permission prompt. Left for later behind more `bell*` keys.
- **`<title> | <session> | webtty`.** Longer than a tab shows; shells that set a title already name the host and directory.
