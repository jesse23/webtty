# ADR 041: client — Own the terminal layer on official libghostty-vt

**SPEC:** [client](../specs/client.md), [config](../specs/config.md)
**Status:** Accepted
**Date:** 2026-10-12

---

## Context

The client's terminal is the npm package `ghostty-web` (pinned at `0.4.0-next.20.g1858a59`): Coder's TypeScript terminal (renderer, input, selection, addons) over a `ghostty-vt.wasm` built from Ghostty `5714ed07` (2025-12-01) plus Coder's `ghostty-wasm-api.patch`. That base has stopped moving with Ghostty:

- **Upstream is slow and the wasm is frozen.** ghostty-web's last commit is from 2026-06-28, and its wasm is still the patched December 2025 Ghostty. Fixes webtty needs wait on releases that may not come.
- **webtty works around it from outside.** ADR 039 sets the renderer's private `devicePixelRatio`; ADR 040 swaps the renderer's private `ctx` and calls `renderLine`; cursor style (ADR 013/015, `cursor.ts`), mouse motion (`mouse.ts`), IME (ADR 038, `compose.ts`) and XTWINOPS size replies (`kitty.ts`) are client-side patches over ghostty-web behaviour. Fractional DPR (coder/ghostty-web#198) and IME (#97/#190) are among the fixes webtty currently carries as private-field workarounds. Private-field casts compile either way, so an upgrade can silently drop a fix.
- **Ghostty now ships the library officially.** libghostty-vt is built for `wasm32-freestanding` from Ghostty main and published per commit at `tip.files.ghostty.org/<commit>/ghostty-vt-small.wasm`, signed with Ghostty's minisign key. A gap analysis of the Coder patch found that every export it adds has an official equivalent or a TS composition: lifecycle/write, modes, hyperlinks, DSR/DA responses (`WRITE_PTY` effect) and the upstream functions ghostty-web uses map one to one; render state and scrollback are composed in TS (`ROW_DATA_CELLS_RAW` plus a per-row style cache; `scroll_viewport` plus `DATA_SCROLLBAR`). The patch's two core edits are not needed: the `render.zig` default-colour fallback becomes "theme colour in TS", and the `Screen.zig` stale-row fix (coder/ghostty-web#180) was not reproduced on the official wasm at `05dcf887` with the #180 stress payload (0 failures over 300 repetitions, against 6–36 failures per 30–60 repetitions on a pre-fix Coder build). That payload is kept as a regression test for the binding.
- **The official wasm has APIs webtty fakes today:** cursor visual style and blink, title/bell effects, cell pixel size via `ghostty_terminal_resize(cols, rows, cell_width_px, cell_height_px)` plus the `OPT_SIZE` callback (so Ghostty answers XTWINOPS 14/16/18/19t and mode 2048; with no callback installed, no report is sent), and render-state `OVERSCAN` with per-row `VIEWPORT_Y` for pixel-smooth scroll.

A spike measured both engines (headless Chrome 155, 200×60, decode cost only, not glyph drawing):

| | ghostty-web as webtty runs it | ghostty-web, one `getViewport` per frame | Official, `CELLS_RAW` |
|---|---|---|---|
| Full-dirty frame, SGR-heavy | 8.8 ms | 0.27 ms | 0.17 ms |
| Full-dirty frame, plain | 8.0 ms | 0.23 ms | 0.17–0.19 ms |
| Typing (one row changes) | 0.30 ms | 0.25 ms | 0.005 ms |

ghostty-web's renderer calls `getLine(y)` once per row, and each call copies and parses the whole viewport. Write throughput (64 KB chunks, no rendering) was about 2–10× higher on the official wasm (e.g. `seq 5000` capture: 41.7 vs 106–111 MB/s; plain ASCII: 84–87 vs 770–863 MB/s).

The spike also found:

- **Parity.** On 7 of 8 real PTY captures (ls, vim, nvim, top, man/less, an SGR/256/truecolor test, `seq 5000`) the engines matched cell for cell (text, fg, bg, flags, width, cursor) over about 3.95M comparisons, with 512-byte and 1-byte writes. This needs DEC mode 2027 (grapheme clustering) on by default, which the Coder patch forces; without it VS16 emoji are width 1. The one remaining difference is a Hindi conjunct (U+0938 U+094D U+0924 U+0947) that the official wasm clusters as one width-2 cell; this looks like the newer Unicode rule for Indic conjuncts (not confirmed).
- **Scrollback is far smaller than configured.** The client passes `Math.ceil(config.scrollback / 80)` as the scrollback limit, and the Coder wasm reads it as bytes. With the default config (`256 * 1024` becomes `Math.ceil(262144 / 80) = 3277`), users get about 500–650 rows at 120 columns (224 at 200×60), far below what the setting suggests; a config value has to be about 80× larger to get its intended row count. `scrollback: 0` becomes a limit of 0, which the Coder patch treats as unlimited.
- **The Coder wasm leaks on truecolor output.** With many distinct truecolor styles, `memory.buffer` grows to 58.75 MB after 20k lines and 261.75 MB after 100k, while keeping about 673 rows. The official wasm holds at 24.44 MB on the same input.
- **The Coder wasm crashes** (`memory access out of bounds`) on the second terminal created in an instance after the first wrote a multi-codepoint grapheme and was freed; `term.write('')` throws `RangeError`. webtty creates one `Terminal` per page (`src/client/index.ts`), so this is not reachable today; it would matter only if a terminal is ever recreated in place (e.g. on font zoom or reconnect).

## Decision

Take ownership of the terminal layer: vendor ghostty-web's TypeScript into webtty, then move it onto the official, unpatched libghostty-vt wasm, in stages that each ship on their own, leave the client working, and can be reverted on their own.

**Scope of this ADR.** This ADR records the direction and the stage plan, and decides steps 1 and 2. Step 2's items are bug fixes in code webtty then owns. Step 3 (official wasm and binding), step 4 (scrollback in lines, client and config) and step 6 (`OVERSCAN` smooth scroll, which supersedes ADR 040 in part) each get their own ADR before they are implemented; the rules below are inputs to those ADRs.

1. **Vendor ghostty-web unchanged.** Copy its `lib/` into `src/client/vendor/ghostty-web/` with its MIT `LICENSE` and a provenance note (upstream repo and commit). Commit the Coder `ghostty-vt.wasm` in the same directory with a sidecar recording npm `ghostty-web@0.4.0-next.20.g1858a59`, Ghostty `5714ed07` plus `ghostty-wasm-api.patch`, the licence (MIT) and its sha256; it stays until step 5. Import from the vendored path and drop the npm dependency. Because the TS is bundled into `client-browser.js`, ghostty-web's `new URL('../ghostty-vt.wasm', import.meta.url)` no longer points at the wasm, so `Ghostty.load` gets an explicit wasm path (`/ghostty-vt.wasm`). `scripts/build.ts` copies the wasm from the vendored path instead of `require.resolve('ghostty-web')`, `src/server/static.ts`/`routes.ts` resolve it from `dist/` or the vendored path instead of `node_modules`, and `static.test.ts` drops `ghosttyWebRootFromMain`. `dist/ghostty-web.js` goes away and `client.html` loads only `client-browser.js` (changes ADR 012's asset list). No terminal behaviour change; the private members webtty uses become ordinary code it owns. Acceptance: the existing tests pass and the served wasm is byte-identical to the npm package's (same sha256).
2. **Fix ghostty-web bugs at source.** One fix per change, each deleting the matching webtty workaround. The list is closed; anything else is a separate change.

   | Fix in vendored ghostty-web | webtty workaround deleted | ADR touched |
   |---|---|---|
   | One viewport read per frame instead of `getLine` per row | none (8.8 → 0.27 ms per frame) | none |
   | Whole-ratio DPR in the renderer | private `devicePixelRatio` set in `index.ts` | 039 |
   | Wheel encoding: SGR scroll when mouse tracking is on, with `mouseScrollSpeed` | wheel intercept in `index.ts` | 017 |
   | Hover motion encoded as Cb=35 | `mouse.ts` `rewriteHoverMotion` | none (bug fix) |
   | Default arrow pointer instead of I-beam | `normalizeCursor` MutationObserver in `index.ts` | none (bug fix) |
   | FitAddon without the 15 px scrollbar reserve | `fit.ts` `computeGrid` | 033 |
   | Textarea keeps focus and follows the cursor cell | focus and positioning half of `compose.ts` | 038 |
   | DECSCUSR applied inside the terminal, with a cursor-cell repaint | `cursor.ts` stream interceptor and ghost-cursor repaint | 013, 015 |

3. **Official wasm and binding, alongside the Coder engine** (own ADR). Add an official binding (`ghostty.ts`) behind the same `GhosttyTerminal` surface, so the renderer, selection and buffer code stay as they are. The binding reads rows through `next_dirty` and `ROW_DATA_CELLS_RAW`; wires `WRITE_PTY`, `BELL`, `TITLE_CHANGED`, `SIZE` and `DEVICE_ATTRIBUTES` through a function-table trampoline; and turns on mode 2027 with `MODE_DEFAULT`. `OPT_SIZE` answers with device-pixel cell sizes as `kitty.ts` does today, and `kitty.ts` stops sending its own size replies on this engine so apps don't get two. `DEVICE_ATTRIBUTES` returns `ESC[?62;22c` and `ESC[>1;10;0c`, as the Coder wasm does (without the callback the official secondary DA is `ESC[>1;0;0c`). Scrollback keeps today's budget: the same derived value goes to `SCROLLBACK_MAX_BYTES`. The engine is chosen at build time with a URL override (`?engine=coder|official`); the default stays `coder` until a parity and browser matrix is recorded (Chrome, Firefox, Safari; resize/reflow; DA/DSR/XTWINOPS/OSC round-trips; the #180 payload), then flips to `official`.
4. **Scrollback in lines** (own ADR, client and config). A new client key `scrollbackLines` (default 10,000) sets `SCROLLBACK_MAX_LINES`, with `SCROLLBACK_MAX_BYTES` at 32 MiB. `scrollbackLines: 0` means unlimited lines: `SCROLLBACK_MAX_LINES` NULL, bytes still 32 MiB. `scrollback` keeps its current meaning, the server's replay buffer in characters (`src/server/websocket.ts`), and the client stops deriving its limit from it. Official engine only.
5. **Delete the Coder engine and the workarounds the official API makes unnecessary**, after one release with `official` as the default: the Coder wasm and its sidecar, cursor style from the render-state cursor, size reports answered by Ghostty through `OPT_SIZE` (deletes the `kitty.ts` size replies; depends on step 3 installing `OPT_SIZE`), the official mouse/key encoders and `terminal_paste`, theme colours from render state.
6. **Pixel-smooth scroll through `OVERSCAN`** (own ADR, supersedes ADR 040 in part). Draw the extra rows the render state provides at a fractional offset, replacing the strip canvas and `renderLine` swap of ADR 040. When it ships, ADR 040 gets a "Superseded in part by" note and the client SPEC's ADR 040 row is updated.

Future work, not decided here: official selection, search, synchronized-output hold (mode 2026), OSC 52 and notifications through effects.

**Rollback.**

- Step 1: revert the change; the npm dependency and `dist/ghostty-web.js` come back.
- Step 2: each fix is its own change; reverting one restores its workaround.
- Step 3: `?engine=coder` falls back per tab; flipping the build-time default back is a one-line change. The Coder engine is kept for at least one release after the default flips.
- Step 4: revert restores the derived byte limit; `scrollback` and the server are untouched, so no config needs migrating back.
- Step 5: git revert only; this is why it waits for a release on the official default.
- Step 6: the ADR 040 path stays until `OVERSCAN` frames are verified in Chrome, Firefox and Safari; reverting restores it.

Rules for the binding and the vendored official wasm (inputs to the step 3 and step 4 ADRs):

- **Commit the wasm.** Vendor the official `ghostty-vt-small.wasm` from a commit that has a tip build, with its `.minisig` (captured from the GitHub `tip` release while that commit is tip; R2 does not serve it) and a JSON sidecar recording the commit, source URL, size and sha256. A script fetches and verifies a new pin against the key in Ghostty's `PACKAGING.md`; the build/test step re-checks sha256, size and signature offline. No network at build time. First pin: Ghostty `05dcf887ef51ea27821f20979493306ec3a19149` (2026-10-12), 780,049 bytes, sha256 `c8a8a0cdd3eeb17951b0c23277d99e1b88016e2afe48f932b37992dfb88607ee`.
- **Scrollback is lines plus a byte ceiling.** Set `SCROLLBACK_MAX_LINES` and `SCROLLBACK_MAX_BYTES` together; never pass 0 bytes (disables scrollback) or NULL for both. A line limit alone does nothing, because the default 10,000-byte cap wins.
- **Wasm memory views do not outlive an export call.** Memory growth detaches the `ArrayBuffer` silently. Rebuild typed-array views after every export call, and copy `CELLS_RAW` rows and callback payloads into JS-owned arrays at once.
- **One binding module.** Every wasm export call lives in the vendored `ghostty.ts`; nothing else in the client touches wasm memory or exports.
- **Layouts come from `ghostty_type_json`.** Struct offsets and enum values are read from the wasm's own manifest at load, not hard-coded, so a pin bump that moves a field fails loudly instead of misreading memory.

Code borrowed from other projects keeps its licence notice and a header naming source repo, commit and path.

### Considered Options

- **Vendor the TS, then move it to the official wasm (chosen)** — owns the code webtty is tuned against, and reaches current Ghostty without carrying a Ghostty diff.
- **Keep depending on ghostty-web (status quo)** — no work now, but the wasm stays on December 2025 Ghostty with its byte-capped scrollback, truecolor memory growth and free/recreate crash, and every fix stays a private-field workaround.
- **Upstream the fixes to coder/ghostty-web and keep the npm dependency** — rejected: the last commit is from 2026-06-28 and the release cadence is unknown, so fixes would wait on someone else's release, and the wasm would still be the patched December 2025 build.
- **Rebase the Coder patch onto current Ghostty** and build the patched wasm with Zig — rejected: carries a Ghostty diff for good, needs Zig in CI, and every Ghostty bump means a patch rebase.
- **Fork ghostty-web as a separate package** — same code ownership as vendoring, plus a publish and version-bump loop for a package only webtty uses.
- **Vendor the TS, keep the Coder wasm for good** — steps 1–2 alone. Fixes the per-row frame cost (8.8 → 0.27 ms) but keeps the frozen, patched wasm and has no `OVERSCAN`.
- **Depend on `@gkoreli/ghostty-vt-js`** — an MIT ghostty-web-shaped TS layer over unpatched Ghostty, but pinned at Ghostty `09557e91` (2026-08-10), 1071 commits behind the pin above. It calls exports the current wasm no longer has (it fails at once with `ghostty_wasm_alloc_u8_array is not a function`), predates `CELLS_RAW`, `next_dirty` and `OVERSCAN`, and replaces FitAddon and the renderer API webtty uses. One maintainer, created 2026-09-19. Borrow its function-table trampoline (`src/wasm/fn-table.ts`, verified to install a `WRITE_PTY` callback on the official wasm) with attribution; do not depend on it.
- **Thin rewrite of the whole terminal** — a new renderer, input and selection on the official API. Most of ghostty-web's TS works and is what webtty is tuned against; rewriting it re-opens every behaviour ADR 013–040 settled.
- **A Zig shim around Ghostty** that exports one bulk-row helper — no Ghostty diff, but adds a Zig toolchain to the build and binds to internal Zig APIs, which are less stable than the C ABI. `CELLS_RAW` with a style cache already matches a bulk copy per frame, so the shim buys nothing measurable.
- **ReleaseFast (`ghostty-vt.wasm`, about 1.06 MB) instead of ReleaseSmall (780 KB)** — left to the step 3 ADR. Frame decode is already about 0.2 ms on ReleaseSmall, so the deciding factor is `vt_write` throughput on a large `cat`, which has not been compared between the two.

## Consequences

- Frame decode drops from about 8–9 ms to about 0.2 ms at 200×60 (from step 2 on), and typing frames to about 0.005 ms (from step 3).
- Scrollback holds about the configured line count up to the byte ceiling (about 32k plain lines at 120 columns under 32 MiB; fewer with truecolor or wide terminals, e.g. 14,271 rows of heavy truecolor under 16 MiB; page granularity can land a few hundred rows under the limit, e.g. 9,588 rows for a 10,000-line limit).
- Wasm memory, measured in Node/V8 (not yet in a browser): about 11 MB per tab at 10,000 lines and 120 columns of plain text, about 25 MB for heavy truecolor, about 56 MB at 300 columns with heavy truecolor. The byte ceiling bounds scrollback pages only; total memory is roughly the ceiling plus the active screen plus allocator and page-pool overhead, which is how a tab can exceed 32 MiB. Step 4 confirms the figures in headless Chrome.
- **Config migration.** `scrollback` keeps its meaning (server replay buffer, default 262144), so existing configs replay as before. Client history moves to `scrollbackLines`: a user who raised `scrollback` to get more terminal history gets the 10,000-line default instead and must set `scrollbackLines`. The config SPEC documents both keys when step 4 ships.
- webtty owns the terminal code: fixes are normal edits with tests, and the `as unknown as` casts into the renderer go away.
- About 780 KB of binary in git per official pin (plus the Coder wasm until step 5), and webtty carries the vendored ghostty-web code (MIT, Coder) from here on.
- **API instability.** libghostty-vt is unversioned and its headers say the API will change (allocator exports, the mode API and colour getters all changed between Ghostty `09557e91` and `05dcf887`). A pin bump is a deliberate change: re-run parity and the binding's tests. The wasm does not record its commit (`ghostty_build_info` reports `0.1.0-dev`); the sidecar is the only record.
- **Memory never shrinks.** Wasm linear memory has no maximum and stays at its high-water mark after `reset` and `free`; compression is unsupported on wasm32. A tab gives memory back only when it closes.
- **Tip-build availability.** Only some main commits get a tip wasm (8 of the last 25 checked), and the `.minisig` is downloadable only while the commit is the current `tip`. Committing the wasm and its signature removes the runtime dependence; pinning an arbitrary commit means a local Zig build.
- **Kitty graphics stays client-side.** It is compiled out of the wasm32 build (`kittyGraphics: false`), so ADR 032's overlay remains.
- **Behaviour changes apps can see.** Primary DA (`ESC[?62;22c`) is unchanged. Secondary DA stays `ESC[>1;10;0c` only because the binding installs `DEVICE_ATTRIBUTES`; step 3 verifies both end to end. Replies that are actually new are the ones the Coder patch dropped: XTWINOPS and mode 2048 size reports from Ghostty (through `OPT_SIZE`), OSC 4/10/11/12 colour queries (a no-op in the Coder patch), DECRQM mode reports, XTVERSION, the kitty keyboard query and ENQ. The Hindi conjunct above takes one wide cell, and newer Ghostty parsing applies everywhere. All of these replies reach the PTY only through the `WRITE_PTY` callback; step 3 installs it, or the official engine answers nothing.
- The official artifact needs wasm SIMD (Chrome 91+, Firefox 89+, Safari 16.4+).
- Not yet measured: glyph drawing cost, Firefox and Safari, resize/reflow parity, OSC/query replies end to end, secondary DA without a callback in a browser, and `OVERSCAN` frames in a browser. The step 3 matrix and step 6 must cover them before the default flips or step 6 ships.
