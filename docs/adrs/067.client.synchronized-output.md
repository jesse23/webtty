# ADR 067: client — Hold painting during an app's synchronized update

**SPEC:** [client](../specs/client.md)
**Status:** Accepted
**Date:** 2026-10-14

---

## Context

Scrolling through a pi session made the text and the images blink. Measured in a headless Chromium on a pi session with 277 messages and an image, recording every compositor frame during a slow trackpad scroll:

- pi tracks the mouse and scrolls its own view. On every wheel tick it redraws the whole screen in one synchronized update (DEC mode 2026, `CSI ? 2026 h` … `CSI ? 2026 l`): it deletes every kitty image placement (`a=d,d=a`), clears and rewrites each row, then places the images again.
- One update is about 13 KB and reaches the browser as about 14 WebSocket messages. The browser can paint between any two of them.
- webtty's render loop painted every frame regardless of mode 2026, and the kitty overlay repainted on the frame after any change. A frame between two messages showed the rows half cleared and the images gone: 12 of 40 frames matched no clean scroll of the frame before.

libghostty-vt tracks mode 2026, but painting is the host's job. Ghostty's renderer does not paint while the mode is on. Its IO thread starts a timer on every `CSI ? 2026 h`, restarting it if one runs (`termio/Thread.zig`, `sync_reset_ms = 1000`), and when the timer fires it turns the mode off (`Termio.resetSynchronizedOutput`) and paints. An app that never ends an update therefore freezes the view for a second, and after that the mode is really off: a DECRQM for 2026 reports it reset, and the next update starts from scratch.

## Decision

- `SyncHold` (`core/sync-hold.ts`) holds painting while the engine's mode 2026 is on, for at most `SYNC_HOLD_MAX_MS` (1000 ms) after the update's last begin.
- **Every begin restarts the time**, as in Ghostty. The write pipeline hands each write's output to `SyncHold.wrote`, which looks for `CSI ? 2026 h` with `scanSyncBegin` (`core/sync-scan.ts`): alone or among other modes (`CSI ? 25;2026 h`), and split across writes, an unfinished sequence carried to the next one. A repeated begin inside an update, or an end and a new begin in one write, starts a new second. A mode turned on in a form the scan does not read (a C1 CSI) is timed from the first frame that sees it.
- **When the time runs out, the mode is turned off** in the engine (`GhosttyTerminal.setMode(2026, false)`, `GHOSTTY_TERMINAL_OPT_MODE`), as Ghostty's `resetSynchronizedOutput` does, so DECRQM, the echo and the next update all see it off.
- **One decision for every painter.** The render loop skips only the render of a held frame: `beforeRender`, the find step, the reply drain and the textarea anchoring still run, so replies are not delayed and a glide keeps its time. The echo render after typed input asks the same `SyncHold`, so it waits too, and renders at once again after the update ends or expires. `Terminal.renderHeld(now)` lets the embedder's own painting follow the same rule: the kitty overlay skips its repaint on a held frame and keeps its dirty state, so it repaints on the first frame after the update.
- `Terminal.reset()` (a reconnect replaces the engine before the replay) forgets the update and any unfinished begin. A replay that ends inside an update holds a second at most, like any other.
- Input devices need nothing of their own: wheel ticks to an app are paced by `TickPacer` (ADR 045), not by painting, and a held frame only batches the app's redraws into the frame after the update.

## Considered Options

- **Buffer the output on the client until the update ends, then write it.** Rejected: the engine already applies the update correctly; only painting it half way is wrong, and buffering would delay replies the app waits for inside the update.
- **Hold only the kitty overlay.** Rejected: the text blinks too, since its rows are cleared and rewritten across messages.
- **Coalesce WebSocket messages on the server.** Rejected: messages split anywhere, and the browser can still paint between two of them.
- **Time the update from the first frame that sees the mode on, and never touch the mode.** The first version did. Rejected: a repeated begin did not restart the second, so back-to-back updates in one stream were cut short, and a stuck mode stayed on in the engine, so the echo, which read the mode directly, never rendered at once again.
- **Feed `CSI ? 2026 l` to the engine on expiry.** Rejected: it would go through the parser in the middle of whatever sequence the output left unfinished; the mode setter changes only the mode.

## Consequences

- Measured again on the same session: 0 of 31 frames scrolling up and 0 of 30 scrolling down were torn, with pi sending the same traffic.
- Any app using synchronized output (pi, Claude Code, neovim, tmux) is painted only between updates, as in Ghostty.
- An app that turns the mode on and never off freezes painting for a second after its last begin; then the mode is off until the app begins another update.
- Each write is scanned for `2026`; output without it costs one `includes` and a look at its last escape.
