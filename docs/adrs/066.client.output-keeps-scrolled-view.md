# ADR 066: client — Output keeps a scrolled-back view on its text

**SPEC:** [client](../specs/client.md)
**Status:** Accepted
**Date:** 2026-10-14

---

## Context

The vendored write pipeline kept coder/ghostty-web's rule: any output while the view is scrolled back moves the view to the bottom (`lib/terminal.ts`, "Auto-scroll to bottom on new output (xterm.js behavior)"). Only a view on a selected find match was exempt (ADR 055). The comment was wrong about xterm.js: xterm.js keeps a scrolled view while the user has scrolled up (`BufferService.isUserScrolling`).

An app that redraws while it works, such as pi's spinner and status line, writes several times a second. Scrolling back slowly through its scrollback then flickers: each wheel step moves the view up a little, and the next redraw pulls it back to the bottom, even when the redraw only rewrites a line in place. `seq` and an idle app write nothing while the view moves, so they scroll smoothly. Running the real engine headlessly confirmed it: a view 10 lines back went to the bottom on a redraw of one status line.

Keeping the view is the industry default: Ghostty (`scroll-to-bottom = keystroke, no-output`), kitty, WezTerm, Alacritty, xterm.js and VS Code, and gnome-terminal all leave a scrolled view where it is on output; only xterm jumps, with `scrollTtyOutput` (on by default). Ghostty, WezTerm and xterm.js pin the view to a row of the buffer; kitty and Alacritty count the lines added and move the view back by as many. webtty already scrolls to the bottom on a key or a paste (ADR 055).

Counting lines by the scrollback's length is not enough. Below the scrollback limit the length grows by the lines added, but at the limit Ghostty prunes whole pages (ADR 046): the length drops by several hundred rows at once (673 at 80 columns with `scrollbackLines: 2000`). A view kept by the length's change jumps by about a page at each prune. libghostty-vt reports neither the lines added nor the rows pruned, but its own viewport is a pin on a row, which Ghostty moves when it prunes: measured on the pinned wasm, a pin 30 rows back stayed on its text through every prune, and a pin on a pruned row went to the oldest row left. webtty already moves that viewport and reads it back for a prompt jump (`promptJumpRow`, ADR 057).

## Decision

On the normal screen, output keeps a scrolled-back view on its text, with Ghostty's own pin:

- **Before each write** the write pipeline pins Ghostty's viewport on the view's top row (`Viewport.pin`, `GhosttyTerminal.pinViewport`: `GHOSTTY_SCROLL_VIEWPORT_ROW`). **After it** the binding reads where the pin went (`GHOSTTY_TERMINAL_DATA_SCROLLBAR`) and puts Ghostty's viewport back at the bottom (`unpinViewport`), and the view goes to that row (`Viewport.unpin`). The same text stays in view through new lines, through rows pruned at the scrollback limit and through a clear: a cleared scrollback brings the view to the bottom, and a view whose own rows were pruned lands on the oldest line left, as in Ghostty. The pin is released in a `finally`, so a write that throws cannot leave Ghostty's viewport off the bottom, where the render state reads it.
- **A smooth scroll's sub-line offset.** Less than a line back, webtty's view is at line 0 and the renderer shows part of the row above (`CanvasRenderer.requestedOffset`). A pin on the active screen follows the output, so that row is pinned instead; it is in view. `Viewport.scrollToBottom` is announced from line 0 too while that row shows, so a key or a paste drops the offset and the view follows the output again.
- **Not a move the user made**: it fires no `onScroll` and does not show the scrollbar.
- **A view at the bottom** pins nothing and follows the output as before. The alternate screen has no scrollback to keep a view in: output there still moves the view to the bottom, dropping a sub-line offset too. A view on a selected find match is kept by the find step as before (ADR 055).
- **`SmoothScroll` follows the kept view** for every input device (ADR 045): a trackpad's deltas applied at once, a mouse wheel notch's ease-out glide, a spinning wheel's and a slow TrackPoint's linear glides, and a fast TrackPoint's spring. After a write it moves its glide by as many lines as the view moved (`Glide.shift`), keeping the fraction, the velocity and, for a timed glide, its start, so the glide goes on covering the distance it had left, frame by frame as without the output. The exception is a glide heading for the bottom: it still ends there (`shift(delta, keepTarget)` stretches a timed glide's remaining curve to start from the moved value, and a spring keeps heading for its target), or a scroll down could never reach output that keeps coming. Writes that do not go through `onOutput` (the status line `PtyConnection` writes after a reconnect) are caught up with on the next frame or wheel event, before the glide moves.

## Considered Options

- **Keep coder/ghostty-web's rule.** Rejected: it is the flicker, and no terminal webtty follows does it.
- **Skip the scroll to the bottom only while a glide is running.** Rejected: a slow scroll is a series of short glides, and a view at rest would still jump on every redraw.
- **Move the view by the scrollback's change in length.** The first version did. Rejected: exact below the limit, but at the limit each page Ghostty prunes moved the text in view by about a page.
- **Count lines in the output (newlines at the bottom margin, as kitty and Alacritty do inside their parser).** Rejected: webtty does not parse the output; scroll regions, reverse index, wrapping and resizes would all have to be redone outside the engine, which already tracks the row.
- **Make it configurable like Ghostty's `scroll-to-bottom`.** Not now: `no-output` is Ghostty's default and the behaviour webtty follows elsewhere. A setting can be added if someone asks for xterm's behaviour.

## Consequences

- Scrolling back while an app streams or redraws is smooth, and the view stays on its text, at the scrollback limit too.
- A write while scrolled back costs three more wasm calls (pin, read, unpin): measured on the pinned wasm, 5,000 one-line writes took 4.3 ms pinned against 3.2 ms unpinned, and the pin does not mark the render state for a full redraw. A view at the bottom costs nothing.
- Coming back to the bottom takes a key, a paste or a scroll, as in Ghostty.
