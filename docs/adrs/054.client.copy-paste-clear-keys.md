# ADR 054: client — Copy, paste and clear-screen keys as Ghostty binds them

**SPEC:** [client](../specs/client.md), [key-bindings](../specs/key-bindings.md)
**Status:** Accepted
**Date:** 2026-10-14

---

## Context

webtty has three keyboard paths to the clipboard: Cmd+C copies the selection (the vendored input handler, any platform), Cmd+V fires the browser's `paste` event, and Ctrl+V reads the clipboard itself (ADR 014, ADR 037), with Shift or Alt held too, so Ctrl+Shift+V already pastes. Two keys a native terminal has are missing:

- **Copy on Windows and Linux.** Ctrl+C must stay the interrupt, and Cmd+C needs a key those keyboards do not use for it. Ctrl+Shift+C is sent to the app as `\x03`, an interrupt, with or without a selection.
- **Clear on macOS.** Cmd+K is encoded like any key (the encoder sends `k`), so it types a `k`.

Ghostty's default bindings (`src/config/Config.zig`, `Keybinds.init`, on `main` at the time of writing):

- **Copy and paste.** `super+c` / `super+v` on macOS and `ctrl+shift+c` / `ctrl+shift+v` elsewhere, bound `performable:` to `copy_to_clipboard` and `paste_from_clipboard`. `performable:` means "only consume the input if the action is able to be performed": with no selection, `copy_to_clipboard` is not performed and the key is encoded for the app as if unbound (`ctrl+shift+c` is `\x03` in the legacy encoding). Outside macOS, `ctrl+insert` is also `copy_to_clipboard` and `shift+insert` `paste_from_clipboard`, both without `performable:`, so they are consumed even when nothing happens; the Linux block later rebinds `shift+insert` to `paste_from_selection` (the X11/Wayland primary selection). Plain `ctrl+v` is not bound anywhere.
- **Clear.** `super+k` is `clear_screen`, `performable:`, on macOS only. `Surface.performBindingAction` returns "not performed" on the alternate screen, so the key goes to the app there (an emulator-side clear would desynchronise a full-screen program's idea of the screen). Otherwise `Termio.clearScreen(history: true)`: clears the selection and erases the scrollback, then
  - **at a shell prompt** (`Terminal.cursorIsAtPrompt`, which needs OSC 133 semantic prompt marks, as fish 4 and Ghostty's shell integration emit), erases the whole screen and sends FF (`0x0C`) to the shell so it redraws its prompt at the top;
  - **otherwise** deletes the rows above the cursor (`eraseActive(cursor.y - 1)`, which shifts the rest up), so the cursor's row becomes the top row and output in progress carries on below it, and deletes all kitty graphics.

  At a prompt Ghostty erases the scrollback first and the screen second, and libghostty-vt's ED 2 moves a screen whose last non-empty row is a prompt into the scrollback (`eraseDisplay(.complete)`, Ghostty #905), so one screen survives in the scrollback; `Termio.clearScreen` marks it `TODO`.

What libghostty-vt gives an embedder, at the pinned commit (`05dcf887`): no clear-screen call, but `GHOSTTY_TERMINAL_DATA_CURSOR_AT_PROMPT` (`cursorIsAtPrompt`, false without semantic prompt marks and on the alternate screen), the cursor position and the active screen, and the VT parser, which does the erasing: `CSI 3 J` erases the scrollback, `CSI n S` scrolls the region up by n rows (on the primary screen the rows go into the scrollback), `CSI n A` moves the cursor up.

Two things are webtty's own. User `keyboardBindings` (ADR 018) are matched by a capture listener on the container first, and the Ctrl+V listener already steps aside for a combo the user has bound. And the server replays the session's recent output on every connect (ADR 007): a clear done only in the client comes back on the next reload.

## Decision

### The bindings

The platform is the browser's (`navigator.userAgentData.platform`, else `navigator.platform`): macOS (and iOS) or anything else, as Ghostty's defaults depend on it.

| Platform | Key | Action | When it cannot be done |
|---|---|---|---|
| macOS | Cmd+C | copy (unchanged, input handler) | browser default |
| macOS | Cmd+V | paste (unchanged, browser `paste` event) | |
| macOS | Cmd+K | clear screen | sent to the app (alternate screen) |
| others | Ctrl+Shift+C | copy | sent to the app (`\x03`) |
| others | Ctrl+Insert | copy | consumed, nothing sent |
| others | Shift+Insert | paste | consumed; the browser's own paste may run |
| all | Ctrl+V, Ctrl+Shift+V (and with Alt) | paste (unchanged, ADR 014) | the browser's own paste may run |

Modifiers match exactly, as Ghostty's triggers do: Ctrl+Alt+Shift+C is not copy. Cmd+C keeps working on every platform, as before.

`shortcuts.ts` maps a `keydown` to one of these (`shortcutFor(event, mac)`); one capture listener on the container in `index.ts`, registered after the `keyboardBindings` listener, performs it. It replaces the Ctrl+V listener, which becomes the "all platforms" row.

**User bindings win.** The listener returns at once for a combo `keyboardBindings` has (`findBinding`), as the Ctrl+V listener did: a binding with `"chars": ""` turns a default off, as `keybind = ctrl+shift+c=unbind` would in Ghostty.

**Performable.** A copy with no selection, and a clear on the alternate screen, are not performed: the listener leaves the event alone and the input handler encodes the key for the app, as Ghostty does. Ctrl+Insert, as in Ghostty, is consumed either way. A paste is performed when the browser has `navigator.clipboard.readText` (the read itself is asynchronous, and a failed read sends Ctrl+V, ADR 014); without it (http other than localhost) the key is kept from the app but not `preventDefault`ed, so the browser's own paste (Ctrl+V, Ctrl+Shift+V and Shift+Insert outside macOS) can still fire the `paste` event webtty handles.

**Shift+Insert pastes the clipboard**, not the primary selection: a page cannot read the primary selection. This is Ghostty's binding outside macOS before its Linux block replaces it, and what Shift+Insert does in a browser on Windows.

### Clear screen

`Terminal.clearScreen()` (vendored `terminal.ts`) does Ghostty's `clear_screen` with what libghostty-vt has, and returns false, doing nothing, on the alternate screen:

- clears the selection;
- **at a prompt** (the binding's new `cursorAtPrompt()`, `GHOSTTY_TERMINAL_DATA_CURSOR_AT_PROMPT`): writes `CSI 2 J` then `CSI 3 J` to the terminal and sends FF to the app through `onData`. The order is the other way round from Ghostty's, so the screen ED 2 moves into the scrollback is erased too: the scrollback ends up empty, which is what `clear_screen` is for;
- **otherwise**: with the cursor on row y > 0, writes `CSI y S` and `CSI y A` (the rows above the cursor scroll off and the cursor follows its row to the top, as `eraseActive` leaves it), then `CSI 3 J`.

The sequences go to the terminal only (`term.write`), never to the PTY; only FF is sent. `index.ts` then clears the kitty graphics placements (`KittyGraphics.clear`, as an ED from the app does; image data is kept for re-placement) and lets the smooth scroll settle at the bottom.

## Consequences

- On Windows and Linux, Ctrl+Shift+C copies a selection, Ctrl+Insert copies, and Shift+Insert pastes; Ctrl+Shift+C with no selection is still an interrupt. Ctrl+C is unchanged.
- On macOS, Cmd+K clears the screen and the scrollback on the normal screen. At a fish 4 prompt (or any shell sending OSC 133) the shell redraws its prompt at the top; at a shell without semantic prompts, the prompt row moves to the top. In vim, less or any full-screen program, Cmd+K is the app's key, as in Ghostty.
- The clear is this tab's own. A reload, a reconnect or another tab on the session replays the session's output from the server, scrollback included, until the program clears it. At a prompt the shell's redraw after FF is replayed as well.
- With a scroll region set on the normal screen (rare at a shell), `CSI y S` scrolls only the region, and the result differs from Ghostty's, which deletes rows regardless.
- `keyboardBindings` can still claim any of these keys.
- The browser's own Ctrl+Shift+C (inspect element in Chrome) is no more reachable than before: the key was already `preventDefault`ed when it was sent as `\x03`.

## Considered Options

- **Bind copy and paste on every platform** (Cmd+C and Ctrl+Shift+C everywhere). Simpler, but Ghostty's defaults differ by platform, and on macOS Ctrl+Shift+C is the app's.
- **Copy on Ctrl+C when there is a selection** (Windows Terminal). Not Ghostty's, and a selection left on screen would turn the next interrupt into a copy.
- **Ghostty's order at a prompt (scrollback first, then the screen).** Leaves the old screen in the scrollback, the `TODO` Ghostty records.
- **Always clear the whole screen and send FF.** Without semantic prompts webtty cannot tell a prompt from a program writing output, and FF to a running program is a stray byte; Ghostty sends it only at a prompt.
- **Clear on the server too, so a reload shows the cleared screen.** The replay is a byte buffer the server does not parse; cutting it at a client's request is a protocol change, and other tabs on the session would lose their history.
- **`RIS` or `CSI 2 J` everywhere.** RIS resets modes the program set; ED 2 alone keeps the scrollback.
