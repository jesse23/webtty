# ADR 043: client — Copy rows on scroll, then overscan

**SPEC:** [client](../specs/client.md)
**Status:** Accepted
**Date:** 2026-10-13 (step 2: 2026-10-13)

---

## Context

The renderer (`src/client/vendor/ghostty-web/renderer.ts`) drew every row on any frame where `viewportY` changed, and on every frame while scrolled up, even when nothing changed. A one-line scroll step on a 175×64 grid draws about 11,000 glyphs, and a terminal left scrolled up in its history draws them 60 times a second. Both engines (ADR 042) go through the same `render()`, so both pay this.

Pixel-smooth scroll (ADR 040) moves the canvas by a CSS offset between lines, so only whole-line moves reach the renderer. Each one still costs a full redraw, and at most one line can be offset before the canvas has to be redrawn.

## Decision

Two steps, both in the renderer and for both engines.

**Step 1: copy the rows still in view.** When the viewport moves by whole lines, by less than a screen, and nothing else changed, `render()` moves the canvas content with one `drawImage` of the canvas onto itself, in device pixels, with identity transform and the `copy` operator. Then it draws only the rows that came into view. `copy` replaces pixels instead of blending them, so a translucent background does not darken. It also clears everything outside the copied area, which is exactly the rows that get redrawn. A frame with nothing changed draws nothing, including while scrolled up.

A partial frame must leave the canvas exactly as a full redraw would. A full redraw draws the rows in order, and each row clears its own cell area first. So a row's pixels are its own cells plus whatever the next row draws over it (tall glyphs, combining marks). Anything the row above drew into it is cleared. To match this, `repaintRows` repaints a run of rows by drawing them in order, plus the row below the run, on a scratch canvas the size of the canvas, unclipped. It then copies the run's rows into the canvas in device pixels, clearing them first so a translucent background is replaced, not blended. A run of every row is drawn on the canvas directly. Repainting follows three rules:

- When a row's content or highlight changes, that row and the row above it are repainted. This covers engine-dirty rows, selection, link hover, and rows that came into view.
- When rows come into view at the top, the last row is repainted too, because the row below it, whose glyphs overflowed into it, scrolled out.
- When only an overlay changes, just its own row is repainted. The cursor is the only such overlay: the row the last frame drew it in, after the copy moved it, unless the same cursor is drawn there again. The same cursor over a row that was not repainted is not drawn again either: it is still there, and a translucent cursor colour drawn over itself every frame builds up to opaque.

This replaces the old rules: every dirty row plus both neighbours unclipped, and a separate cursor-line redraw on every frame while the cursor blinks.

Copying is skipped, and every row is drawn, whenever any of the following holds:

- `forceAll` is set, the canvas was resized, or the engine reports a full redraw.
- The theme, font, metrics or device pixel ratio changed since the last frame (`canvasStale`).
- The viewport moved by a fraction of a line, or by a screen or more.
- The scrollback length changed, or the engine reports any dirty row. While scrolled, any dirty row also forces a full redraw on a frame with no move.
- Selection rows were marked dirty. They are viewport rows from when they were marked.
- The last frame drew the scrollbar and this one does not, so no row keeps the old thumb. This also fixes text under the scrollbar staying hidden after the fade-out.
- The last frame was drawn without a scrollback provider while scrolled, which leaves its top rows blank. The visibility repaint in `index.ts` does this.
- The browser restored a lost context (`contextrestored` on the canvas). The backing store is blank and the context state reset, so the canvas is resized too. A frame that draws nothing would otherwise leave it blank, and a copy would copy the blank rows.

Things that move with the copied rows need no extra handling: the selection (anchored to buffer lines), OSC 8 hover underlines (keyed by hyperlink id) and the edge strips (ADR 035), which copy the canvas' edge pixels. The regex link underline is drawn at fixed canvas rows, so on a copied frame it is cleared where the copy moved it and drawn where it is.

The official engine reported every row dirty while scrolled, and a full redraw on returning to the bottom, so the old renderer would repaint. It now reports the real dirty state. Output still marks a full redraw, because it snaps the view to the bottom.

Screen scrolling caused by output is not copied. The engines report which rows changed, not that the screen scrolled, and detecting a scroll by comparing rows (including graphemes and hyperlinks) is not cheap or safe enough for this step.

**Step 2: overscan.** The renderer draws into a canvas of its own that holds `overscan` rows above and below the viewport (`DEFAULT_OVERSCAN`, 16). Canvas row k shows viewport row k − 16 at a viewportY the renderer picks (the band). Pixel-smooth scroll (`smooth-scroll.ts`) sets the sub-line offset on the renderer (`setScrollOffset`), and `render()` moves the canvas up by `translateY` and clips it to the viewport with `clip-path`. A scroll within the band changes only those two styles. A scroll past it picks a new band half the overscan further in the direction of the move, and copies the rows still in the canvas with step 1's `shiftRows`. This replaces ADR 040's one-row strip canvas and its `renderLine` context swap, which drew a row on every wheel event.

The terminal's canvas element keeps its layout box and the mouse events, and draws nothing. The drawing canvas is inserted before it, absolutely positioned with no offsets, so it sits at the element's static position wherever fit's padding moves it. It ignores the mouse and is excluded from the terminal canvas lookups like the edge strips. Fit, the edge strips, Kitty graphics and the IME anchor still measure the element. Hit testing (`terminal.ts`, `selection-manager.ts`) subtracts `scrollOffset`, because viewport row 0 starts that far below the element's top. Kitty images are drawn that far lower too, so they move with the text. The edge strips copy the drawing canvas (`visibleArea`): the right strip the column of the part in view, the bottom strip the last pixel line of the last row in view, which at a fraction of a line is below the clip. The line the clip ends on runs through that row's glyphs, and stretched across the padding it streaks on every frame. An offset set for a taller cell, before a font change, is shown as at most a line, so the row above always covers the gap. Fit re-splits the scroll position after every DPR and font change, as under ADR 040, so the offset is snapped to the new device-pixel grid and cell height instead of waiting for the next wheel event.

Each canvas row has a state: invalid, *joined* (its own cells plus what the next line draws into it, as a full redraw leaves a row), or *cut* (its own cells only). Every frame, the rows in view are brought to the state a full redraw of the viewport leaves them in. The last row is cut, the others are joined, and at a fraction of a line the row above the viewport is cut, as ADR 040's strip drew it alone. Rows out of view are not drawn until they come into view, so a move draws only the rows that came into view plus the edge rows that change between joined and cut, and no frame draws the whole band. `repaintRows` draws a run of rows on the scratch canvas, which is now only as tall as the run plus the next line. It draws on the canvas directly only when the run is cut and the rows around it are invalid, as after a full redraw. Changes invalidate rows instead of repainting them:

- A changed row (engine, selection, link hover) invalidates itself and, when it is joined, the row above.
- An overlay (the cursor, the scrollbar) invalidates only its own row. The scrollbar is painted over the rows in view; rows it no longer covers are invalidated.
- Output at the bottom (new scrollback or any dirty row) invalidates every row out of view, since the lines may have moved. While scrolled it still repaints the viewport, as in step 1.
- Selection and regex link ranges are tracked in canvas rows. The selection is anchored to buffer lines like the canvas rows, so it repaints only when it changes; `SelectionManager.getSelectionRange` gives it unclamped. The regex link range is in viewport rows, so a scroll repaints where it was and where it is. A hyperlink hover change repaints every row that is not invalid and has the old or new id.
- After a copy, the tracked cursor row, scrollbar rows, selection and link range move with the rows. "None" is `null`, not −1: a copied row index can be negative.

Both engines read the rows outside the viewport through the scrollback provider and the screen rows, as for the viewport. The official engine's render-state `OVERSCAN` is not needed.

## Considered Options

- **Offscreen double buffer.** Copy to a second canvas and back. That is two copies of the whole canvas per scroll; the scratch canvas only ever copies the repainted rows. Drawing the canvas onto itself works in Chrome: the browser check below found no difference from a full redraw.
- **`object-position` on the taller canvas, with the element itself as the window.** One element, no hit-testing changes, and the box clips. Chrome rounds `object-position` to whole CSS pixels (−10.5px shows what −10px shows), so at DPR 2 every half-pixel offset was one device pixel off. `translateY` places to the device pixel.
- **Drawing every row of the band (eagerly) on a full redraw and on a new band.** That is up to 96 rows instead of 64 for each full redraw, and a band change draws 8 rows at once. Drawing rows when they come into view costs the same per line and keeps output at the bottom as cheap as before.
- **Joined rows at the viewport edges.** Without the cut last row and cut row above, a line crossing draws nothing when its rows are drawn. But at rest the last row would show what the line below draws into it (box-drawing stems, accents on capitals, emoji), which a full redraw of the viewport does not.
- **Drawing the run on the canvas, clipped to it.** Chrome skips a glyph whose box lies outside the clip, even where its antialiased edge reaches inside. A combining mark of the row below whose top sits just under the run (the diaeresis of `ạ̈`, the stack of `ặ`) then loses the faint edge it draws on the run's last device-pixel line: up to 21 levels on about 10 pixels per row. Copied frames carry those pixels along until the next full redraw. Clip edges through the middle of a row avoid it in practice, but not for every glyph height.
- **Unclipped neighbour rows (the old dirty-row rule).** Drawing a row again over an unchanged neighbour draws its overflow twice, which differs from a full redraw on anti-aliased edges.

## Measurements

### Step 1

Times are the script time of all `requestAnimationFrame` callbacks in one frame, including the edge strips' copy of the canvas:

| At the bottom, idle with a blinking cursor | 0.17 / 0.31 ms (175 `fillText`) | 0.04 / 0.04 ms (none) |

In the browser, the canvas after whole-line steps (1 to 5 lines, up and down, back to the bottom) was compared with a full redraw of the same position by `getImageData`. It was identical for both engines at DPR 1, 1.5 and 2. Reading a canvas back makes Chrome draw it on the CPU from then on, and pixels drawn before and after that switch differ by up to 2 levels. So each check first reads the canvas back, then redraws it in full, then compares.

Unit tests (`renderer.test.ts`) draw into a rasterising fake canvas where glyphs overflow into the rows above and below, and, like Chrome, a glyph whose cell is outside the clip is not drawn. They check that each step draws at most the new rows plus four, and that the result equals a fresh full redraw at DPR 1 and 1.5. A third test does the same at DPR 2 with a selection, a hovered link range and the cursor.

### Step 2

Bun with a recording fake canvas (`scrollbench`: 175×64, DPR 2, 3,000 lines, best of 3). Per frame: glyphs drawn and canvas pixels copied (the self-copy plus the scratch copies). Step 1 also counts ADR 040's strip row, which was drawn on every frame at a fraction of a line:

| Per frame (official / Coder) | Step 1 | N = 4 | N = 16 | N = 64 |
|---|---|---|---|---|
| One-line steps, `fillText` | 416 / 216 | 416 / 216 | 416 / 216 | 416 / 216 |
| One-line steps, Mpx copied | 5.46 / 5.46 | 1.03 / 1.16 | 0.44 / 0.50 | 0.27 / 0.30 |
| Trackpad, 0.3 line per frame, `fillText` | 319 / 213 | 209 / 141 | 209 / 141 | 209 / 141 |
| Trackpad, 0.3 line per frame, Mpx copied | 1.64 / 1.64 | 0.35 / 0.36 | 0.15 / 0.16 | 0.10 / 0.10 |
| Trackpad, 1.4 lines per frame, Mpx copied | 5.46 / 5.46 | 1.50 / 1.60 | 0.65 / 0.69 | 0.38 / 0.40 |

Glyphs per line step stay the same: the rows that come into view are drawn either way, and the edge rows that turn joined or cut replace step 1's row below the new rows. What goes is the copy of the whole canvas on every line, and the strip row on every fractional frame. N = 16 copies an eighth of step 1. N = 64 copies little less and makes the canvas three times as tall (about 60 MB instead of 20 MB at 175×64, DPR 2); N = 16 is 30 MB. An idle frame costs 1–2 µs in both.

Headless Chrome 155, 1400×900 at DPR 2, the same mixed output. Script time of `requestAnimationFrame` callbacks plus wheel handlers, per frame:

| (official / Coder) | Step 1 | N = 16 |
|---|---|---|
| Wheel handlers, trackpad | 0.21 / 0.10 ms | 0.009 / 0.011 ms |
| Wheel handlers, line steps | 0.21 / 0.07 ms | 0.04 / 0.04 ms |
| Canvas copied, line steps | 0.40 / 0.40 Mpx | 0.04 / 0.04 Mpx |
| Canvas copied, trackpad | 0.19 / 0.19 Mpx | 0.02 / 0.02 Mpx |
| `fillText`, trackpad 3.3 px events | 71 / 72 | 25 / 25 |

The total script time per frame is 0.2–0.9 ms in both builds, and differs from run to run by more than the two differ, so it is not given. Most of the wheel handler time was the strip. The copies are GPU work that script time does not show.

Screenshots of the step 1 and step 2 builds were compared at 37 scroll positions per run. The positions include trackpad and line steps up and down, jumps past the overscan, the top and the bottom of the scrollback, a selection and a parked, faded scrollbar. They were compared for the official engine at DPR 2 and the Coder engine at DPR 1, 1.5 and 2. Every viewport row was identical, and so was the bottom edge strip, which extends the last row's own last pixel line in both. The differences were all in places step 1 got wrong:

- **The row above the viewport, at a fraction of a line.** At DPR 2 and 1.5, ADR 040's strip sat one device pixel below the canvas grid (the band matches step 1's shifted down by one row). Its last pixel line was hidden and the line above it showed. At DPR 1 it is identical. The strip also drew the row unselected; it is now drawn with the selection.
- **The scrollbar while fading**, which depends on when the screenshot was taken.

A Kitty image placed with text after it moves with that text at a fraction of a line. Under ADR 040 it stayed behind.

Unit tests (`renderer.test.ts`) check the rows in view against the step 1 renderer drawn independently. The viewport is drawn as a screen of its own lines, and the row above on its own. Positions are trackpad and line steps up and down, jumps past the overscan and the top of the scrollback, at overscan 1, 2, 3 and 16 and DPR 1 and 2. A fixed pseudo-random run of 500 steps per overscan mixes scrolls, output, selection, regex and OSC 8 hover and scrollbar changes, and checks each step against a full redraw. Further tests cover a hover change on a row just out of view, output at the bottom followed by a scroll, a selection change on a frame that copies rows, the translucent cursor, a restored context, and the number of rows a scroll draws.

## Consequences

- Scrolling through scrollback draws only the rows that came into view. A terminal parked in scrollback draws nothing.
- The canvas is the same as a full redraw after every partial frame, including glyph overflow from the row below. An exception is a glyph that reaches more than one row up. A later browser check never read the canvas back: after each of 39 states on the Coder engine and 45 on the official one (whole-line and trackpad scrolling, selection, cursor shapes, typing, output while scrolled, clear, alt screen, resize), with emoji, ZWJ sequences, flags, stacked combining marks, Devanagari and wide characters, it compared a screenshot with a screenshot after a forced full redraw. All were identical. The first version drew runs clipped on the canvas and failed this check (see Considered Options).
- The scratch canvas is as large as the canvas: about 20 MB more at 175×64 cells, DPR 2. Each partial repaint adds one copy of the repainted rows.
- A blinking cursor no longer redraws its row on every frame, only when it toggles.
- A frame that drops the scrollbar repaints every row. That is once per scrollbar fade-out, and once after a resize or font change, which now pass the current scrollbar opacity instead of drawing it at full opacity.
- Output that scrolls the screen still redraws every dirty row, which is every row.
- Pixel-smooth scroll moves the canvas by CSS across up to 16 lines and draws only the rows that come into view and the edge rows. It no longer draws a row on every wheel event or copies the whole canvas on every line.
- The drawing canvas is a second element next to the terminal's canvas. Code that reads the terminal's pixels must use `visibleArea`, and code that maps mouse positions to rows must subtract `scrollOffset`.
- The canvas is 1.5 times as tall (about 30 MB at 175×64, DPR 2). The scratch canvas is only as tall as the largest run drawn on it.
- Self-copy `drawImage`, the `copy` operator and step 2's moved and clipped canvas were checked in Chrome only. Firefox and Safari still need the same check.
