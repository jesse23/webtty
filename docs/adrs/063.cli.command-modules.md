# ADR 063: cli — Command modules with injected dependencies

**SPEC:** [architecture](../specs/architecture.md), [cli](../specs/cli.md)
**Status:** Accepted
**Date:** 2026-10-14

---

## Context

- `src/cli/index.ts` parses `argv` and dispatches at import time; `--dir` handling and the `go` aliases are not tested in-process.
- `src/cli/commands.ts` (369) holds nine commands and the byte formatters for `key`. Each calls `fetch`, `console` and `process.exit` directly; `go` and `run` repeat "ensure the server, then GET or POST the session". `run` is about 110 lines covering two modes (warm-up and exec) and re-implements NDJSON line splitting.
- `src/cli/http.ts` is misnamed: it holds the config-derived URL helpers, server process management (with its own src/dist path arithmetic) and the browser opener.
- `commands.test.ts` (1020 lines) spies on module namespaces (`spyOn(httpModule, …)`), which depends on ESM live bindings and breaks when a module is split.

## Decision

- **`main.ts`** (`main(argv, deps)`) is the CLI's composition root; `index.ts` stays the entry (`dist/cli/index.js`, the `bin`) and only calls it. `cli-args.ts` (`parseArgs`, pure, including `--dir` at the end of `argv`) and `help-text.ts` are pure.
- **`CliDeps`** (`cli-deps.ts`): `{ client, config, out, err, write, exit, version, server, openBrowser, editor, tty }`, built once from the real globals by `createCliDeps()` (the default for `main`'s `deps` parameter, so `index.ts` only calls `main(process.argv)`). `config` is `loadConfig`, read on every call; `write` is raw stdout/stderr for `run`'s streamed output; `server` is `{ start, stop }` over `server-process.ts`; `editor` (`EditorHost`) and `tty` (`KeyTty`) are the process-facing hosts of `edit-config` and `key`. Nothing is read when the deps are built, so `-v` and `help` never touch the config file. Every command takes `(args, deps)` (or the `Pick<CliDeps, …>` it needs), so tests capture output and the exit code without subprocesses or namespace spies.
- **`api-client.ts`**: `WebttyClient(baseUrl, fetch, openSocket)`, where `baseUrl` is a string or a function read on every request and `fetch`/`openSocket` default to the globals, with `isRunning`, `listSessions`, `ensureSession` (the one copy of ensure-or-create), `removeSession`, `renameSession`, `stop`, `execute` (an async iterator of NDJSON messages over the shared `LineSplitter`) and `openPty` (opens and closes the session's PTY socket, for `run`'s warm-up). `configuredClient()` builds the client for `loadConfig().port` on 127.0.0.1. A request that gets no response throws `ServerUnreachableError`; commands catch only that error to print their "not running" message and let any other error propagate.
- **`server-process.ts`**: `resolveServerEntry({ cliDir, runningFromSrc, useNode })` (pure, four cases tested), `startServer`, `stopServer`. **`browser-opener.ts`**: `openBrowser`, `toBrowserHost`, `sessionPageUrl`.
- **`commands/`**: one file per command (`go`, `list`, `remove`, `rename`, `start-stop`, `edit-config`, `run`, `key`) plus `key-format.ts`; `run.ts` is two functions, `warmUp` and `exec`.
- `commands.test.ts` and `http.test.ts` split by command and migrate from namespace spies to injected deps in the same commits as the split.
- Output text, exit codes, flags and aliases stay byte-identical. Tests that start a server keep a temporary `HOME` so `loadConfig().port` never resolves to the user's configured port.

## Consequences

- Each command is a short file testable in-process, and coverage counts the CLI.
- The CLI's HTTP calls are in one client, so a route change on the server has one place to follow on the CLI side.

## As built

Recorded when the documentation was reconciled with the code (2026-10-14).

- The CLI is as decided: `main.ts` (110 lines), `cli-deps.ts`, `api-client.ts` (215 lines, the largest CLI file), `server-process.ts`, `browser-opener.ts` and the nine files under `commands/`. `commands.test.ts` and `http.test.ts` are gone; each module has its own test on injected deps (`cli/test-support/`).
- `cli/index.test.ts` is the one subprocess check of the entry. CLI coverage is 100% of lines and functions.
