# ADR 038: client — Composition (IME / dictation) text at the cursor

**SPEC:** [client](../specs/client.md)
**Status:** Accepted
**Date:** 2026-10-09

---

## Context

macOS dictation (and IME input such as Pinyin or Japanese kana) shows its in-progress text as a *composition*: the browser fires `compositionstart` / `compositionupdate` / `compositionend` and renders the uncommitted text in whichever editable element has focus. In webtty, that text appears on a new line under the terminal, in the browser's default text color. The extra line pushes the canvas up until the composition ends.

The cause is in how ghostty-web (`Terminal.open`) sets up input:

- The `#terminal` container gets `contenteditable="true"` and `tabindex="0"`. ghostty-web also adds a hidden `<textarea>` (1×1px, `opacity: 0`, `clip-path: inset(50%)`, pinned at `left: 0; top: 0`) for keyboard and IME input.
- Only a `mousedown` on the **canvas** moves focus to the textarea. A click in the padding (ADR 033/034) or the edge extension (ADR 035) focuses the **container**. `term.focus()` and the browser's initial tab focus also go to the container.
- When the container has focus, the browser inserts the composition as a text node after the `<canvas>`. ghostty-web removes that node only at `compositionend` (`cleanupCompositionTextNodes`), so it is visible while dictation runs. It uses the body's default color and font and wraps onto its own line under the canvas.
- When the textarea has focus, the composition is invisible because the textarea is clipped. The macOS dictation and IME candidate panels then anchor to the textarea's position at the top-left corner instead of the cursor.

The committed text already reaches the PTY through `compositionend` → `onData` in either case, so input is not lost. Only the preview is in the wrong place and has the wrong style.

## Decision

The client takes over how composition is presented. The data path that ghostty-web's `InputHandler` sends to the PTY stays the same.

1. **One input target.** All text input goes to ghostty-web's textarea. A `focusin` listener on the container sends focus back to the textarea whenever the container itself gets focus. This covers clicks in the padding or edges, tab focus and `term.focus()`. A window `focus` listener does the same when the window comes back with the container still focused, because `focus()` in a background window moves `activeElement` without firing `focusin`. Because the container never holds focus, the browser never inserts composition text nodes into it. `contenteditable` stays on the container because ghostty-web's own handlers expect it.
2. **Anchor the textarea at the cursor.** On every animation frame, move the textarea to the pixel position of the terminal cursor cell, writing only the styles that changed. ghostty-web's `onRender` never fires and `onCursorMove` only reports row changes, so neither can drive this. The position is `term.buffer.active.cursorX` / `cursorY`, shifted down by `viewportY` and clamped to the grid, multiplied by the cell size from `renderer.getMetrics()`, and offset by the canvas position inside the container. The textarea stays anchored even before a composition starts, because macOS places the dictation microphone when dictation begins. The textarea gets the cell's line height. macOS then places the dictation microphone and the IME candidate window at the cursor.
3. **Show a themed preview at the cursor.** Add a small overlay element (`src/client/compose.ts`) with absolute position and `pointer-events: none`, placed over the cursor cell. It is updated from `compositionupdate` (`event.data`) and hidden on `compositionend` or `blur`. It uses the terminal's `fontFamily` and `fontSize`, `theme.foreground` on `theme.background`, and an underline, which is the usual style for uncommitted text. Long text is not wrapped and runs to the right edge. The textarea stays invisible, so the overlay is the only visible copy of the composition.

## Considered Options

- **Remove `contenteditable` from the container.** This would stop the stray text node. However, ghostty-web adds the attribute deliberately and its `beforeinput` guard depends on it. Removing it would also leave a focused container that accepts no IME input at all. Sending focus to the textarea fixes the same problem without patching ghostty-web's assumptions.
- **Make the textarea itself visible and styled at the cursor.** This needs no overlay, but browsers style textareas inconsistently (caret, selection highlight, scrollbars, padding). The textarea would also show text the user typed directly and not only the composition. A separate overlay that only displays text is easier to control.
- **Write the preview into the terminal (local echo).** This would mix uncommitted text into the remote application's screen state, and the application would then redraw over it. It is not done.
- **Fix it in ghostty-web upstream.** The upstream issue is [coder/ghostty-web#97](https://github.com/coder/ghostty-web/issues/97), and [coder/ghostty-web#190](https://github.com/coder/ghostty-web/pull/190) fixes the same causes. webtty pins an exact ghostty-web version, so the fix in the client unblocks users now. Once a ghostty-web release includes the upstream fix, bump the pin and remove `src/client/compose.ts`.

## Consequences

- The dictation and IME preview appears at the cursor in the theme's colors, and the layout no longer shifts during composition.
- The system dictation and IME panels follow the cursor.
- The behavior relies on ghostty-web's public `textarea`, `buffer.active` cursor and `renderer.getMetrics()`, which the client already uses for fit, edge extension and kitty graphics. It also assumes that ghostty-web leaves the textarea's position alone except during its right-click copy flow, which the client detects and skips.
- Committed text still goes through ghostty-web's `compositionend` → `onData` path, so its de-duplication against `beforeinput` stays unchanged.
- Verify manually with macOS dictation and at least one CJK IME in Chrome and Safari, and test Linux and Windows IMEs if they are available. The cursor-to-pixel placement is unit-tested in `compose.test.ts`.
