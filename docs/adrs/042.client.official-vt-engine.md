# ADR 042: client — Official libghostty-vt engine behind `?engine`

**SPEC:** [client](../specs/client.md)
**Status:** Accepted
**Date:** 2026-10-12

---

## Context

ADR 041 step 3 adds a binding to Ghostty's official, unpatched libghostty-vt wasm next to the Coder engine, behind the `GhosttyTerminal` surface the renderer, selection and buffer code already use, and leaves the details to this ADR. Its rules for the binding (commit the wasm and signature, verify offline, one binding module, layouts from `ghostty_type_json`, no wasm memory views across export calls, never 0 bytes or NULL for both scrollback limits) apply here unchanged.

ADR 041 left ReleaseSmall (`ghostty-vt-small.wasm`) against ReleaseFast (`ghostty-vt.wasm`) open, to be settled on `vt_write` throughput. Both builds from Ghostty `05dcf887` were measured (Apple M3 Pro; 120×40; mode 2027 on through `MODE_DEFAULT`; `SCROLLBACK_MAX_BYTES` 3277; 64 KiB `vt_write` chunks; no rendering; a fresh instance per run, build order alternated; medians of 10 runs in Bun and 8 in each browser). "Mixed" is 20 MiB of word lines with 1,219,849 SGR sequences (16-colour, 256-colour and truecolor foregrounds, bold with background, italic with underline, resets); "plain" is 20 MiB of the same words without SGR.

| | ReleaseSmall | ReleaseFast |
|---|---|---|
| Size | 780,049 B (gzip -9: 280,250) | 1,057,238 B (gzip -9: 346,187) |
| Bun 1.3.11, mixed / plain | 141.6 / 478.7 MiB/s | 141.9 / 515.0 MiB/s |
| Headless Chrome 155, mixed / plain | 154.6 / 704.2 MiB/s | 162.2 / 701.8 MiB/s |
| Headless Firefox 157, mixed / plain | 120.5 / 500.0 MiB/s | 127.4 / 540.5 MiB/s |

ReleaseFast is 0–8% faster. A 20 MiB SGR-heavy `cat` spends 0.13–0.17 s in `vt_write` on ReleaseSmall and about 0.01 s less on ReleaseFast. With step 4's 32 MiB byte ceiling (Bun, 4 runs) the gap is the same: mixed 135.7 against 138.5 MiB/s, plain 438 against 478.8 MiB/s. Wasm compile was under 1 ms in Chrome and 2–5 ms in Firefox for both.

The Coder wasm, and the official wasm (`05dcf887`, ReleaseSmall) with the callbacks decided below, reply as follows (probed in Bun):

| Query | Coder wasm | Official, binding as decided below |
|---|---|---|
| DA1 `CSI c` | `ESC[?62;22c` | `ESC[?62;22c` |
| DA2 `CSI > c` | `ESC[>1;10;0c` | `ESC[>1;10;0c` (`ESC[>1;0;0c` without the callback) |
| DA3 `CSI = c` | none | `DCS ! \| 00000000 ST` (with or without the callback) |
| XTWINOPS `14/16/18 t` | none (`kitty.ts` answers) | `ESC[4;h;wt`, `ESC[6;ch;cwt`, `ESC[8;rows;colst` from `OPT_SIZE` |
| XTWINOPS `19 t`, mode 2048 | none | `ESC[9;rows;colst`, `ESC[48;rows;cols;h;wt` |
| OSC 4/10/11 `?` | none | colour report, once the theme colours are set |
| XTVERSION `CSI > q` | none | `DCS >\|libghostty ST` (no callback installed) |
| DSR `6n` | `ESC[r;cR` | same |
| ENQ | none | none (no callback installed) |

Scrollback was measured on the first 4 MiB of the same plain and mixed payloads, 64 KiB writes, at the derived default budget (3277: `SCROLLBACK_MAX_BYTES` on the official wasm, `scrollbackLimit` on the Coder wasm):

| Size, payload | Coder wasm | Official wasm |
|---|---|---|
| 120×40, plain | 409 rows | 512 rows (+25%) |
| 120×40, mixed | 525 rows | 584 rows (+11%) |
| 200×60, plain | 351 rows | 378 rows (+8%) |
| 200×60, mixed | 261 rows | 243 rows (−7%) |

The official wasm keeps more rows in three cases and 7% fewer in one. ADR 041's figures (500–650 rows at 120 columns, 224 at 200×60) came from a different payload and are not compared here.

## Decision

Add the official engine as a second engine behind one interface, selectable per tab with `?engine=official`, with `coder` as the default until the acceptance matrix below is recorded.

**Files.**

```
src/client/vendor/
  ghostty-vt/                          ← official wasm, not edited
    ghostty-vt-small.wasm              ← Ghostty 05dcf887, ReleaseSmall, 780,049 B
    ghostty-vt-small.wasm.minisig      ← from the GitHub `tip` release while 05dcf887 was tip
    ghostty-vt-small.wasm.json         ← commit, source URL, minisig source, public key, size, sha256
    LICENSE                            ← Ghostty's MIT licence at the pinned commit
    PROVENANCE.md
  ghostty-web/
    ghostty.ts                         ← both engines: Coder (existing) and official (new)
    fn-table.ts                        ← function-table trampoline, borrowed (see below)
    LICENSE.ghostty-vt-js              ← fn-table.ts's MIT licence
  ghostty-vt.test.ts                   ← offline sha256, size and signature check
  official-terminal.test.ts            ← the official binding on its own (cells, modes, replies, keys)
  engine-parity.test.ts, fixtures/     ← both engines on the PTY captures and the #180 payload
src/client/engine.ts                   ← DEFAULT_ENGINE and the `?engine` override
scripts/update-ghostty-vt.ts           ← fetch and verify a new pin (network; run by hand)
```

ADR 041's "one binding module" holds: every wasm export call and memory access for both engines is in `ghostty.ts`. `fn-table.ts` receives `__indirect_function_table` from `ghostty.ts` and only adds and recycles entries in it. It is copied from `gkoreli/ghostty-vt-js` at `248de81a188b71a1919d3c5c5bce2f99a836b5b1`, `packages/ghostty-vt-js/src/wasm/fn-table.ts` (MIT), with that licence notice and a header naming repo, commit and path. Its notice and Ghostty's licence go into `dist/THIRD_PARTY_LICENSES`. Biome excludes `src/client/vendor/ghostty-vt/` like the vendored TS, since the update script writes the sidecar; the tests in `src/client/vendor/` stay under Biome.

**Engine interface.** In `ghostty.ts`, `GhosttyTerminal` becomes an interface with today's public method set (lifecycle, render-state reads, `getViewport`/`getLine`, scrollback and grapheme reads, hyperlinks, modes, `hasResponse`/`readResponse`), implemented by `CoderTerminal` (the current class, renamed) and `OfficialTerminal`. `Ghostty.load(path, engine)` returns an engine with `createTerminal(cols, rows, config)` and `createKeyEncoder()`. The renderer, selection, buffer and input handler keep importing `GhosttyTerminal` and `KeyEncoder`; only the renderer changes: `IRenderable` gains an optional `setViewportOffset?`, which `render` calls first (below). The interface gains:

- `setCellPixelSize(width, height)`: device-pixel cell size, as `kitty.ts`'s `deviceCellSize` computes it today from the renderer's CSS cell metrics and `window.devicePixelRatio` (the ratio `graphics.ts` uses). `terminal.ts` calls it at the points listed under `SIZE` below. A no-op on Coder.
- `resize(cols, rows, cellWidthPx, cellHeightPx)`: today's `resize` with the device-pixel cell size added, so a change of both grid and pixels is one call. Coder ignores the pixel arguments.
- `setViewportOffset(linesFromBottom)`: the terminal's `viewportY`. `renderer.render` calls it first with the `viewportY` it was given, so every render path (the loop, `writeInternal`'s `awaitingEcho` render, font change, scrollbar fade, `index.ts`'s `visibilitychange` repaint) syncs in one place; reads between renders use the last offset. Not implemented on Coder.
- `readEffects(): { bell: boolean; title: string | null }`: bell and title changes since the last write. Coder returns none, and `terminal.ts` keeps its stream scan for BEL and OSC 0/2 only on Coder.
- `answersSizeQueries: boolean`: true on official. The graphics overlay (`graphics.ts`) then stops sending `kitty.ts`'s `sizeReply`, so apps get one reply per query.

Every existing read keeps the Coder engine's coordinates on both engines, so the renderer, selection and buffer code need no change: `getLine(n)`, `getViewport`, `getCursor` and `isRowDirty(n)` use active-screen rows, and `getScrollbackLine(i)` counts from the oldest scrollback row. `terminal.ts` drains `readResponse` after `write`, after `wasmTerm.resize` and `setCellPixelSize`, and after each frame's render, not only after `write`.

**Binding (official).**

- Rows: a refresh runs `ghostty_render_state_update`, then `ghostty_render_state_row_iterator_next_dirty` and one `ghostty_render_state_row_get_multi` per dirty row for `ROW_DATA_CELLS_RAW` and `ROW_DATA_VIEWPORT_Y`. Each row is decoded straight into JS-owned `GhosttyCell` objects, with bit positions from the `GhosttyCell` descriptor in `ghostty_type_json` and colours and flags from a per-row style cache (`ghostty_render_state_row_cells_get` `STYLE`, only for a style id not yet seen). Graphemes are read only for cells tagged as graphemes. The JS copy is indexed by viewport row. At the bottom (`viewportY` 0) the viewport is the active screen, so `getViewport`, `getLine(n)` and `isRowDirty(n)` read copy row `n`.
- Refresh and dirty rules. The renderer and the Coder-style reads call `update()` many times per frame (`renderer.ts` `render` through `getCursor`, `needsFullRedraw` and `getLine`; selection through `getLine` once per row) and rely on dirty state persisting until `clearDirty()`/`markClean()`. The binding keeps a generation counter, bumped by `write`, `resize`, a `setCellPixelSize` that calls `ghostty_terminal_resize`, a viewport move in `setViewportOffset`, and `reset`. The viewport moves a page read makes, and its move back, do not bump it. A second counter, the content generation, is bumped by all of these except the viewport move; it keys the page cache below. `update()` refreshes only when the generation has changed since the last refresh; otherwise it returns the stored dirty state without an export call. So `getLine`, `getViewport` and `getCursor` always reflect the latest write, as they do on Coder, and a fully dirty frame decodes each row once however often `update()` is called. Each refresh ends with `ghostty_render_state_clean`, which clears both the global `DIRTY` and every per-row `ROW_OPTION_DIRTY` (`render.h`: `update` does not clear either layer), so the next refresh decodes only rows changed since. Decoded cells carry the default fg/bg and palette colours, but Ghostty marks no row dirty when only the defaults change (OSC 10/11/110/111 and DECSCNM leave `DIRTY` false, because its renderer applies them globally; a palette change is `FULL`). So each refresh compares the default colours and the 256-entry palette with the previous refresh and, if any changed, decodes every row and reports full. The rows it decoded go into a JS dirty set, and the global state it returned is kept as the highest seen (none, partial, full). Both accumulate until `markClean()` empties them. Renders outside the render loop (`writeInternal`'s `awaitingEcho` render, `index.ts`'s `visibilitychange` repaint, ADR 040's `renderLine`) go through the same `update()`.
- Cursor: `getCursor` reads `DATA_CURSOR_X`/`DATA_CURSOR_Y` (active-screen coordinates), not the render state's viewport cursor.
- Scrollback: `getScrollbackLength` reads `DATA_SCROLLBACK_ROWS` (S below). Writes never leave the view scrolled, but `terminal.ts` `writeInternal` calls `wasmTerm.write` first and `scrollToBottom()` after it (xterm behaviour), and `smooth-scroll.ts` `onOutput` then drops its sub-line offset. So `OfficialTerminal.write` itself moves Ghostty's viewport to `BOTTOM` before `vt_write` whenever it is scrolled, sets its offset to 0 and marks every row dirty; pruning and screen switches then happen with the viewport at the bottom, and any render before `scrollToBottom` (the `awaitingEcho` render) passes a stale `viewportY` that `setViewportOffset` moves back. A scrolled frame (k = `floor(viewportY)` > 0) follows user scrolling, and S changes under it only through resize and reflow. `setViewportOffset` moves Ghostty's viewport with `ghostty_terminal_scroll_viewport` `ROW` to row S − k (`ROW` counts from the top of scrollback, `viewportY` from the bottom) whenever k or S differs from the last move. Reflow moves Ghostty's viewport with the rows it shows even when S is unchanged, so a resize while scrolled moves it back to `ROW` S − k itself, before any read. The frame is read through the same render-state path, and copy row y maps to `getScrollbackLine(S − k + y)` for y < k and to `getLine(y − k)` for y ≥ k. Those reads are served from the copy. `isRowDirty` returns true for every row while scrolled, since the renderer repaints all rows then anyway. Back at the bottom (`viewportY` 0, including the snap after a write), the binding scrolls Ghostty's viewport with `BOTTOM` and marks every row dirty for the next frame.
- Reads outside the viewport (`getLine(n)` for n ≥ rows − k, scrollback rows above the viewport, smooth scroll's row above the top, selection copy and the buffer API) are read a page at a time through the render state, not cell by cell. On a miss the binding moves Ghostty's viewport with `scroll_viewport` `ROW` to the page of `rows` rows that holds the row, reads the page with `CELLS_RAW` through a second render state, and moves the viewport back before returning: to `BOTTOM` when the offset is 0, to `ROW` S − k otherwise. `scroll_viewport` `ROW` n with n ≥ S snaps to the active screen (`PageList.zig` `scroll`), so a page starts at min(n, S) and rows are mapped from that start. Pages are cached until the content generation changes, so a viewport move keeps them: while scrolled by 0 < k < rows, the renderer's `getViewport` reads the k active rows below the view from the cache instead of decoding them again on every step. A render state's update consumes the terminal's dirty state (page and row dirty bits and the terminal-wide full-redraw flags; `render.zig` `beginUpdate` assumes it is the only consumer), so the second state would hide changes from the primary. Before a page read the binding therefore refreshes the primary when the generation has changed, so the primary has captured every pending dirty bit and flag (and the palette) before the second state runs; this ordering is what keeps the primary correct. The reverse also holds: the second state cannot trust dirty bits the primary has already cleared, and `beginUpdate` rebuilds a row only on a pin, screen or size change or a dirty bit (`render.zig`), so a page read at the same row after an in-place write, or after pruning recycled a page at the same address, would return stale cells. The page-read state is therefore freed and recreated whenever the content generation has changed, so every miss after a content change rebuilds every row it reads. A viewport move alone changes no row, pin or size of the rows already read, so the state is kept across it. Copying a selection over N rows costs about N / rows page reads plus one decode per row, and smooth scroll's row above the top is a cache hit on most frames. `ghostty_terminal_grid_ref` is kept for single-cell lookups (hyperlink hover, a grapheme outside the copy). Per-cell `grid_ref` costs one lookup plus cell, style and grapheme calls per cell (`grid_ref.h` notes the lookup's cost): a 3,000-row selection at 200 columns would be over 1.8 million export calls, and step 4 raises scrollback to 10,000 lines.
- Callbacks through `fn-table.ts`, installed per terminal and released after `ghostty_terminal_free`. None re-enters `vt_write`; each copies what it needs and returns.
  - `WRITE_PTY`: copies the bytes into the queue that `readResponse` drains, the path `terminal.ts` already uses for Coder replies. Replies also arise outside `write` (the mode 2048 report from `ghostty_terminal_resize`), so `terminal.ts` drains at the three points listed above.
  - `BELL`, `TITLE_CHANGED`: set flags. The title is read with `DATA_TITLE` after `vt_write` returns, copied, and handed out by `readEffects`.
  - `SIZE`: fills `GhosttySizeReportSize` with rows, columns and the cell pixel size Ghostty last received. `ghostty_terminal_resize(cols, rows, cellWidthPx, cellHeightPx)` stores the pixel size, ends synchronized output and, with mode 2048 on, sends a report on every call, even with unchanged dimensions (`terminal.h`). So the binding makes exactly one call per real change, and `terminal.ts` supplies the pixels at three fixed points:
    - `open()`, after `createTerminal` and before the first write: `setCellPixelSize` with the initial metrics, so `SIZE` replies never use 0 px. Mode 2048 cannot be on yet, so this sends no report.
    - `Terminal.resize()`, which already returns early when columns and rows are unchanged: it computes the pixel size and calls `wasmTerm.resize(cols, rows, w, h)`, one `ghostty_terminal_resize` with the new grid and pixels.
    - A new `Terminal.syncCellPixelSize()`, called at the end of `index.ts` `fit()`. Every metrics or DPR change reaches `fit()`: font zoom calls it directly after setting `fontSize`, and the `document.fonts.ready` remeasure and `watchDevicePixelRatio` go through `scheduleFit`. If the grid changed, `resize` has already sent the new pixels and this does nothing; if only the pixels changed, `setCellPixelSize` makes one call at the current grid.

    `setCellPixelSize` returns at once when the size equals the one Ghostty last received. Nothing is flushed from the render loop, so the order of the fit's and the render loop's `requestAnimationFrame` callbacks does not matter. A unit test drives `OfficialTerminal` over the real wasm exports with `ghostty_terminal_resize` counted, through the calls `terminal.ts` and `fit()` make, and asserts one `ghostty_terminal_resize` for a zoom that changes grid and pixels, one for a zoom or DPR change that keeps the grid, and none for repeated fits. The refresh, scrolled-view and page-read logic is tested on the real wasm in `engine-parity.test.ts`, against the Coder engine: scrolled reads (`getLine`, `getScrollbackLine`, rendered rows) at several k, a write while scrolled, a resize while scrolled, a write that dirties active rows followed by a page read and then a render, a scrolled page read, an in-place write, a render with the stale `viewportY`, then the same page read again, and the offset stepped through 0 < k < rows, k = rows and beyond and back, before and after an in-place write.
  - `DEVICE_ATTRIBUTES`: primary conformance 62 with feature 22, secondary type 1, firmware 10, ROM 0, tertiary unit id 0. This gives `ESC[?62;22c` and `ESC[>1;10;0c`.
  - `ENQUIRY`, `XTVERSION`, clipboard, notification and the other effects are not installed (ADR 041 future work).
- Setup: `MODE_DEFAULT` with mode 2027 on, so RIS keeps grapheme clustering. The theme's foreground, background, cursor and palette are set through `COLOR_FOREGROUND`, `COLOR_BACKGROUND`, `COLOR_CURSOR` and `COLOR_PALETTE`. The colour values in `GhosttyTerminalConfig` cannot be used as they are: `terminal.ts` `parseColorToHex` encodes an unset colour as 0 ("use default" in `types.ts`), and the default theme's background `#000000` (`src/config.ts`) also becomes 0. `buildWasmConfig` therefore adds a mask of the theme keys that parsed (foreground, background, cursor and the 16 palette entries), which Coder ignores. A key in the mask is set as given, so `#000000` is black. Foreground and background are always both set: libghostty-vt has no default for them, and its render state copies the default colours only when both are set (`render.zig`, the `bg_fg` block), otherwise keeping white on black and ignoring the given colour, OSC 10/11 and DECSCNM. An unset one falls back to the Coder engine's effective default (foreground `0xcccccc`, background `0x000000`). An unset cursor stays unset, and unset palette entries and entries 16–255 come from `COLOR_PALETTE_DEFAULT`.
- Scrollback budget unchanged: the same `Math.ceil(config.scrollback / 80)` goes to `SCROLLBACK_MAX_BYTES`. `scrollback: 0`, unlimited on the Coder wasm, becomes 32 MiB, because 0 bytes disables scrollback and the binding never passes NULL for both limits. `SCROLLBACK_MAX_LINES` stays unset until step 4.
- Keys: the official `KeyEncoder` translates ghostty-web's `Key` and `KeyEncoderOption` values to the official `GhosttyKey` and `GhosttyKeyEncoderOption` values from `ghostty_type_json`. It matches by name, with a fixed rename table for the 44 keys whose names differ (e.g. `GRAVE` → `BACKQUOTE`, `ZERO` → `DIGIT_0`, `UP` → `ARROW_UP`, `KP_*` → `NUMPAD_*`) and for `KITTY_KEYBOARD_FLAGS` → `KITTY_FLAGS`. Twenty-nine keys have different numbers in the two builds, so no value is passed through untranslated. It allocates with `ghostty_wasm_alloc` and `ghostty_wasm_free`.

**Served wasm.** `scripts/build.ts` copies `ghostty-vt-small.wasm` to `dist/`. The server serves it at `GET /ghostty-vt-small.wasm` as `application/wasm`, resolved from `dist/` or `src/client/vendor/ghostty-vt/` like `/ghostty-vt.wasm` (ADR 041 step 1); like that wasm, the server does not start without it. The client fetches only the selected engine's wasm.

**Selection.** `src/client/engine.ts` exports `DEFAULT_ENGINE = 'coder'`, compiled into `client-browser.js`. `?engine=coder` or `?engine=official` in the page URL overrides it for that tab; any other value uses the default. Nothing is stored, and a reload keeps whatever the URL says.

**Verification, offline.** `ghostty-vt.test.ts` (part of `bun test`) checks the committed wasm against its sidecar (size and sha256) and verifies the `.minisig` with `node:crypto`: the Ed25519 signature over the wasm's BLAKE2b-512 hash and the global signature over the trusted comment, both against Ghostty's key from `PACKAGING.md` (`RWQlAjJC23149WL2sEpT/l0QKy7hMIFhYdQOFy0Z7z7PbneUgvlsnYcV`, key id `F5787DDB42320225`). The key is a constant in the test, and the test also asserts that the sidecar records the same key. `scripts/build.ts` refuses to copy a wasm whose size or sha256 does not match the sidecar. Neither step uses the network. `scripts/update-ghostty-vt.ts --commit <sha>` is the only networked step: it downloads from `tip.files.ghostty.org/<sha>/` and the GitHub `tip` release, checks that both give the same sha256 and that `tip` points at `<sha>` before and after the download, verifies the signature, and writes the wasm, `.minisig`, sidecar and Ghostty's `LICENSE` at that commit. `--verify` re-runs the offline check. The minisign verifier is exported from the script and imported by the test, so the script and the test check the same way; the test holds its own copy of the key.

**ReleaseSmall.** Vendor `ghostty-vt-small.wasm`. ReleaseFast's 0–8% throughput gain is about 0.01 s on a 20 MiB `cat`. It does not justify 277,189 more bytes per pin in git and per page load (the server does not compress), or re-running the spike's parity, #180 and memory results, which were all measured on ReleaseSmall.

**Acceptance matrix before the default flips to `official`.** Every check runs on `?engine=official`. Rows marked "vs Coder" compare the result with the Coder engine on the same input; rows marked "official" check replies the Coder wasm does not give. Chrome and Firefox are automated headless, each with its own profile. Safari is checked by hand; safaridriver is not enabled. The results are recorded in this ADR's "Acceptance record" section, with date, browser versions and Ghostty pin, in the change that flips `DEFAULT_ENGINE`.

|---|---|---|
| Browsers | vs Coder | Load, type, render, select and copy, paste, IME, wheel and mouse apps in Chrome, Firefox and Safari |
| Resize/reflow | vs Coder | Normal-screen reflow of wrapped lines when shrinking and growing; alternate screen; font zoom and DPR change re-report cell pixels. After growing, the Coder wasm's `getScrollbackLine` returns stale cells past the old width, so there the official engine is checked against the written text |

The captures are re-recorded from a clean `HOME` before they are committed as fixtures, so no local paths are committed.

**Rollback.** Before the flip, the official engine is reached only through `?engine=official`, and reverting the commit removes it. After the flip, `?engine=coder` falls back per tab, and setting `DEFAULT_ENGINE` back is a one-line change. The Coder engine stays for at least one release after the flip (ADR 041 step 5).

### Considered Options

- **ReleaseSmall (chosen)** — smallest download; parity, memory and #180 already measured on it.
- **ReleaseFast** — 0–8% more `vt_write` throughput for 35% more bytes (see Context).
- **Official binding in its own module** (e.g. `ghostty-vt.ts`) — smaller files, but splits wasm access across two modules, against ADR 041's one-binding rule.
- **Engine chosen in config** (`GET /api/config`) — needs a config key that step 5 deletes, and a server change to try an engine. A URL parameter is per tab and needs neither.
- **Answer size queries in `kitty.ts` on both engines** and leave `OPT_SIZE` unset — then mode 2048 and `19 t` stay unanswered, and step 5 could not delete the `kitty.ts` replies.
- **Read rows through `grid_ref`**, every row or only those outside the viewport — the header marks `ghostty_terminal_grid_ref` as not for performance-sensitive use, and it works one cell at a time. The render state's dirty rows and `CELLS_RAW` are the bulk path that the spike's 0.17 ms full frame and 0.005 ms typing frame were measured on, and page reads reuse it for selection copy and the buffer API.
- **Selection text from Ghostty's formatter** (`ghostty_formatter_format` with a selection) — one call per copy, but selection and buffer code would change to use it, and they read cells, not text. Page reads keep them as they are.

## Consequences

- `?engine=official` runs the official wasm with real effects: bell and title from Ghostty, query replies through `WRITE_PTY`, and size replies from Ghostty with device-pixel cells.
- Apps on the official engine see new replies: DA3, XTWINOPS `19 t`, mode 2048 reports, OSC 4/10/11 colour reports, DECRQM and XTVERSION `libghostty`. DA1 and DA2 are unchanged. ENQ stays silent: it needs the `ENQUIRY` callback, which this step does not install, although ADR 041's Consequences list ENQ among the new replies.
- Scrollback under the default config holds −7% to +25% of the Coder engine's rows, depending on size and payload (see Context), until step 4.
- The repo carries 780,049 more bytes of wasm, plus the signature, the sidecar, `fn-table.ts` and the fixtures. Pages using the Coder engine download no new wasm; `client-browser.js` grows by about 37 KB minified (108 → 145 KB, uncompressed) for the official binding, which is bundled whichever engine runs.
- `ghostty.ts` holds two engines until step 5 deletes the Coder one.
